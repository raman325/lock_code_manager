**Finding (low severity):**

`custom_components/lock_code_manager/providers/zigbee2mqtt.py:376` — a slot whose read timed out is marked as answered by any later `users` entry for that slot, even an old one. That wrongly marks a lock that can't report its codes as one that does, and that can't be undone.
- **Why it happens:** the branch `elif user_id in self._late_reads and user_id not in unanswered: self._note_answered()` checks neither `replayed` nor whether the entry is new. The code's own comment a few lines below says Zigbee2MQTT republishes its full cached state on every attribute change. So an old entry for the slot passes for a late answer. That breaks the rule this branch set elsewhere (commit c032656a): a replayed or stale state is not the lock answering.
- **Scenario:** a lock that has never answered, with 5 silent reads in a row.
  1. The silent slots are added to `_late_reads`.
  2. `_async_device_responds` then asks for the lock state, and Zigbee2MQTT replies with its full cached state, including `users`.
  3. The cache holds an old entry for one of those slots that isn't `not_supported_255`: from a `user_status` query, from Zigbee2MQTT's persisted state, or from a retained message replayed on resubscribe.
  4. That entry calls `_note_answered()` and records the lock as answering, which is permanent. `_answered_since_read_began()` then returns True, and the check that would record it as not answering is skipped.
- **Result:** every later poll comes back all-unreadable without raising, because the device still responds. Allocation counts every slot as occupied, and the repair that would let the user allow those slots is never raised. The lock can never get new users.
- **Possible fix:** skip this branch when `replayed` is set, and only count entries that differ from `_last_users_states`.
