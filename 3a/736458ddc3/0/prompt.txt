**Finding**

- `custom_components/lock_code_manager/providers/_mqtt.py:329` — **Medium.** A bridge outage in the middle of a read can wrongly mark a working lock as one that never answers.
  - **Why:** the five silences are counted with nothing checking that the bridge was up while they happened. The lock-state check that follows (`_async_device_responds`) only asks whether the lock answers now. The entity's availability is checked once, at the start of the operation, in `_async_ensure_operational`.
  - **Scenario:** most existing Zigbee locks have no stored verdict yet, because this PR adds the verdict. Zigbee2MQTT restarts during the roughly 50 seconds of silent reads, for example after an add-on update or an adapter reconnect. A drop in Home Assistant's own MQTT connection does the same if publishes still don't raise; I didn't check that.
    - The requests to the `.../get` topic are published without error but nobody receives them, so each slot times out.
    - Zigbee2MQTT is back by the time of the lock-state request, and the lock really does answer it.
    - The lock is recorded as not answering. This doesn't depend on `last_seen`, because the reply is a real one.
  - **Effect:**
    - The lock's codes aren't read for up to an hour, until the hourly probe gets an answer.
    - A fixable repair appears asking the user to allow slots it can't see to be treated as free. If they agree, allocation can overwrite codes set at the keypad on a lock that does report its codes.
    - While the lock is marked this way, its polls never fail, so a lock that is actually gone is never reported offline.
  - **Possible fix:** reset or abandon the count if the entity or bridge became unavailable during the read, or check availability again before recording the verdict.
