**Why this is a regression and not just a pre-existing provider limitation:** before this change the user chose the start slot, which was the only lever for saying "my codes live at 1-5, start at 6." That lever is gone, the existing-codes confirmation is gone from the UI path (`async_step_ui` no longer calls `_find_occupied_lock_slots` / `async_step_existing_codes_confirm`), and `strings.json` now promises *"Lock Code Manager picks which code slot each user occupies, skipping any slot that already holds a code"* — a promise the read cannot keep on 4 of the 7 providers. The same hole reappears in the options flow: adding a lock to an existing entry queries that lock via `_maybe_confirm_then_persist` (`config_flow.py:866`), but the new lock is not yet in any entry's config, so `managed_slots` for it is empty and the existing-codes confirmation never fires either. That is the "silently collide" case you asked about, and it has the identical root cause.

**Fix direction:** `_LockQuery.codes == {}` from a provider whose read is scoped to `managed_slots` must be `None` (unknown), not empty. Either give `BaseLock` a capability flag ("this read enumerates the whole lock" vs "this read only answers about slots I name") that `_occupancy_from` consults, or have those four providers enumerate the device's full slot range from `async_get_capabilities()` rather than from `managed_slots` when asked for occupancy. ## Is a separate provider method justified?

**Yes — but the ZHA half of it should be collapsed the way the z2m half was.**

**Duplication introduced.** ZHA is the only real cost: `async_get_users` (zha.py:340-378) and `async_get_occupied_indices` (zha.py:381-410) are two ~25-line loops that both do `_get_connected_cluster()` → iterate → `cluster.get_pin_code(n)` → `_parse_pin_response`, differing only in the range source, the occupancy predicate, and the error policy. z2m faced exactly this and solved it by extracting `_async_read_slot`; ZHA did not. That is not just repetition — finding #4 above *is* the two loops having silently drifted apart on the occupancy predicate. Extracting a `_async_read_index(slot) -&gt; tuple[status, pin] | None` and having both call sites share it would have forced the disagreement into the open. Everywhere else the duplication is ~10 lines of comprehension over a read that already exists, which is not worth optimising.

**Cost of the alternative.** Widening the shared read is not viable, on two counts:

1. *Hot path.* `async_get_usercodes` is what the coordinator polls on every update (`coordinator.py:442`) and every drift hard-refresh (`coordinator.py:286, 473`). On ZHA and z2m it costs one device round trip per slot. Widening from `managed_slots` (a handful) to advertised capacity (Zigbee `NumberOfPINUsersSupported` is commonly 30–250) turns every poll into 30–250 round trips, each holding `_aio_lock`, with a 10 s per-slot timeout on z2m — minutes per poll on a flaky lock, against a 5-minute interval. Occupancy is needed once, during a config flow; the poll runs forever. Bounding the work at the caller is the whole point.
2. *Blast radius.* Coordinator data has four consumers beyond sync: the websocket payload (`websocket.py:597`), diagnostics (`diagnostics.py:98, 161`), and `_check_duplicate_code` (`_base.py:481`). Widening pushes unmanaged slots' credentials — including readable PINs on zwave_js/z2m/akuvox — into diagnostics and the dashboard payload, and makes `_check_duplicate_code` start raising `DuplicateCodeError` against codes LCM does not manage. `_project_users_to_slots` also seeds `managed_slots → empty()` as a load-bearing contract (sync treats a slot missing from coordinator data as unavailable, `sync.py:416`); widening the seed changes what "missing" means.

Worth noting the premise needs one correction: `async_get_users` is not uniformly scoped to `managed_slots`. `_project_users_to_slots` (`_base.py:1352`) *seeds* managed slots as empty and then overlays every credential the provider reports, including unmanaged ones ("Occupied slots the lock reports that are not managed are surfaced too"). zwave_js and matter genuinely read the whole device; only zha, z2m, akuvox and schlage scope their own `async_get_users`. That is exactly why the zwave_js override reads as free — and why sourcing it from `async_get_usercodes` instead costs nothing and fixes finding #1.</result>

## 1. HIGH — `_cleared_slot` survives a failed set, so a live PIN can be reported as cleared

`custom_components/lock_code_manager/domain/sync.py:521-536`

The two flag writes are both **post-await**:

```python
if snapshot.active_state == STATE_ON:
    await self._lock.async_internal_set_usercode(...)   # ← raises here
    self._last_set_pin = snapshot.credential_state
    self._cleared_slot = False                          # ← never reached
```

The polarities are not equivalent. `_last_set_pin` is a *value* compared against the current desired value at `sync.py:489`, so a stale one is automatically wrong and forces a re-set — failing safe. `_cleared_slot` is a *bare bool* whose stale value is the trusting one, and the only thing that clears it is a **successful** set.

Concrete sequence (all three steps are ordinary tick behaviour):

1. Slot disabled → clear issued → `_cleared_slot = True`, masking lock reports `unreadable` → IN_SYNC.
2. Slot re-enabled → `_perform_sync` set → the write **lands on the lock** but the call raises. This is not hypothetical for this codebase — it is the documented #1397 mode (SET lands, verification GET times out → `LockOperationFailed`). `sync.py:929-942` catches it, `_cleared_slot` is still `True`.
3. Slot disabled again before any successful set (directly, or via the SUSPENDED→OUT_OF_SYNC path at `sync.py:659-675` once the breaker trips — a target change resumes it). `calculate_in_sync` → inactive + unreadable → `return self._cleared_slot` → **True**.

Result: the in-sync sensor reads `on`, no clear is ever issued, and the lock is holding a working PIN in a slot the user disabled. Under the old behaviour that PIN got cleared (annoyingly, forever, but cleared).

I verified this with a direct driver against the real `_perform_sync` / `calculate_in_sync` (mock lock raising `LockOperationFailed` on set): after step 3, `_cleared_slot is True` and `calculate_in_sync(...) is True`, with exactly one clear ever issued.

Fix that works — invalidate **before** the write, not after it:

```python
if snapshot.active_state == STATE_ON:
    self._cleared_slot = False   # a set that raises may still have landed
    await self._lock.async_internal_set_usercode(...)
    self._last_set_pin = snapshot.credential_state
```

I applied exactly this and re-ran the full suite: `1531 passed, 3 skipped` (the one failure is the pre-existing flake in finding 3). Note what that also means — **the whole suite passes either way**, see finding 6.
