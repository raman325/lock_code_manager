## CRITICAL — the migration's device-move is a no-op in production, and its test can't detect that

`/Users/raman/projects/lock_code_manager/custom_components/lock_code_manager/__init__.py:461-465`

```python
device = dev_reg.async_get_device(
    identifiers={
        build_slot_device_identifier(config_entry.entry_id, slot_num)
    }
)
```

`async_get_device` takes `set[tuple[str, str]]`. This passes a set containing a bare **string**. Every other call site in the repo gets it right — `__init__.py:1305`, `__init__.py:1576`, `diagnostics.py:169-173`, and critically `entity.py:56-57`, which is what actually *creates* these devices:

```python
identifiers={(DOMAIN, build_slot_device_identifier(config_entry.entry_id, slot_num))}
```

The lookup misses a dict index keyed by tuples, so it returns `None` — no `TypeError`, no log. I verified this directly against the project's own venv: with a device registered the production way, the tuple lookup finds it and the bare-string lookup returns `None`.

**Why the test doesn't catch it.** `tests/test_init.py:2140-2145` builds the device with the *same* malformed identifier the buggy code searches for:

```python
identifiers={build_slot_device_identifier(config_entry.entry_id, 1)},
```

Bug and test agree with each other and disagree with production. I changed only that one line to the tuple form and re-ran: still green — because entity setup re-parents the device anyway. But that is precisely the path the code comment (lines 454-457) exists to avoid. With the corrected identifier, HA logs:

&gt; Detected that custom integration 'lock_code_manager' **assigns an existing device to a different config subentry** … this silently moves the device.

`homeassistant/helpers/device_registry.py:1947-1954` — `breaks_in_ha_version="2027.8.0"`.

**Failure scenario:** every installation upgrading from v4 takes the deprecated implicit path instead of the deliberate one. One warning per slot device on every startup today; a hard failure on HA Core 2027.8. The migration is a one-way door with no code-level rollback, so this lands silently on all upgraders.

**Fix:** `identifiers={(DOMAIN, build_slot_device_identifier(config_entry.entry_id, slot_num))}` — and fix the test the same way, so it stops validating its own assumption. Note `slot_num` there is `subentry.data.get(CONF_SLOT)`, which is `None`-able by type; migration's `placed` filter makes it safe today, but the `.get` invites `"{entry_id}|None"` later.

## 1. HIGH — `clear_credentials: false` only honours the first name

`/Users/raman/projects/lock_code_manager/custom_components/lock_code_manager/__init__.py:1946-1947`

```python
retained_pairs = runtime_data.retained_pairs
runtime_data.retained_pairs = set()
```

`async_delete_users` stages every departing user's `(lock, slot)` pairs into `runtime_data.retained_pairs` (`domain/services.py:581`) and then makes **one** call to `async_write_entry_config`. But that function is now N writes, not one: `domain/config.py:647` calls `async_remove_subentry` once per departing user, and HA's `_async_update_entry` starts each update listener as an **eager** task. So pass 1 begins executing inside the *first* `async_remove_subentry`, drains the whole `retained_pairs` set, and matches it against a diff that contains only the first user. Pass 2 (started inside the second `async_remove_subentry`) finds `retained_pairs` empty and calls `async_release_managed_slot` on the second user's slot.

Reproduced: entry with `Guest0` (slot 3) and `Guest1` (slot 4), two locks.

```yaml
action: lock_code_manager.delete_user
data:
  config_entry_id: ...
  name: [Guest0, Guest1]
  clear_credentials: false
```

`async_release_managed_slot` was called with `[4, 4]` — Guest1's PIN was wiped from both locks despite the explicit hand-off. Guest0's was correctly retained. The service is documented as "Lock Code Manager stops managing those slots and whatever is programmed there keeps working"; for everyone after the first it does the opposite, irreversibly.

The fix is to discard pairs as they are consumed rather than draining wholesale — e.g. `runtime_data.retained_pairs -= diff.pairs_removed` after the loop, keeping the rest for the passes still to come.

## 2. HIGH — deleting a user while the entry is unloaded leaves the PIN on the lock

`/Users/raman/projects/lock_code_manager/custom_components/lock_code_manager/__init__.py:946-947`

The only thing that clears a departing user's credential is the update listener, and it is registered in `_setup_entry_after_start` and torn down by `async_on_unload`. HA's `async_remove_subentry` has no integration hook — it removes the subentry, the entities and the device, and schedules `entry.update_listeners`, which is empty when the entry is not loaded. v6 is the first release where a user can be deleted without going through LCM code at all; in v5 both routes (`delete_user` service via `get_loaded_config_entry`, and the options flow via `_allocate_for`) required a loaded entry.

Reproduced: set up the entry, `async_unload`, `async_remove_subentry` for `test1` (slot 1), reload. After reload the lock still reports `{1: SlotCredential(present=True, pin='1234')}` and no entry manages slot 1. The same applies to a disabled entry, and to one sitting in `SETUP_ERROR` — which is exactly the state reauth exists for, so "lock entity missing → reauth → user tidies up the roster while they're in there" is a plausible path.

Nothing recovers it: `async_sweep_unmanaged_codes` runs only from `async_migrate_entry`, and the setup pass diffs against `EntryConfig.empty()` so `pairs_removed` is always empty. The PIN keeps opening the door and the slot number is burned (allocation refuses a number it can still read a code on). This is the `#1453` failure mode through a new door.

`_async_prune_orphaned_slot_devices` (`__init__.py:1593`) already computes the exact signal at setup — slot devices whose number is no longer configured — so the cheapest fix is to release those pairs on the locks before pruning the devices.

## 3. MEDIUM — `_async_write_and_settle` can release while a pass is still running

`/Users/raman/projects/lock_code_manager/custom_components/lock_code_manager/domain/services.py:60-67`

Same root cause as #1: one logical write is now N listener wakes. `settled` is set by whichever pass finishes first, not the last, so a service returns while later passes are still working.

Reproduced: four guests, `delete_user` with all four names, with one lock's `async_release_managed_slot` slower than the others (a sleeping Z-Wave node, say). The call returned after 6 of 8 credentials had been cleared.

The `_async_write_and_settle` docstring already concedes "another write landing at the same time can release the wait early" — but that was written when a single logical operation produced a single pass. It is now the normal case for any multi-name `add_user`/`delete_user`, and the promise the function exists to make ("a script that adds a user and then sets their PIN through the new text entity would find nothing to set") no longer holds for batches. Note `test_add_user_service_returns_once_the_entities_exist` and `test_delete_user_service_returns_once_the_entities_are_gone` both use a single name, so neither covers this.

If `async_write_entry_config` returned how many entry updates it made, the waiter could count settle events instead of waiting for one.
