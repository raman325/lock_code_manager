1. **`custom_components/lock_code_manager/domain/coordinator.py:370` — `_last_seen` can hand back the PIN we just wrote instead of what the lock held.** When sync drops a pending write because the user changed or disabled the slot (`drop_pending` at `sync.py:876`), the write's `previous` is thrown away. But `data` still holds the written PIN that `record_write` put there. The next write or clear then takes that PIN as `previous`.
   - Scenario: the slot holds A (cache shows A). The user sets B, and the driver reports it as unknown. Before the deadline, the user changes it to C. Sync drops B and writes C, and C's `previous` is B, not A.
   - The confirmation read still shows A. A is not treated as stale (it isn't B), so C is counted failed immediately and the slot takes a strike.
   - Same for disabling instead: `record_unconfirmed_clear` stores B as `previous`. The first stale read of A ends the trust, and sync sends one more clear.
   - This is the stale-cache case the PR sets out to handle, and it contradicts the docstring ("what the lock was last seen to hold, past any write of ours").

2. **`custom_components/lock_code_manager/domain/coordinator.py:419` — a write-back loses the slot's real old code for the next write.** `record_write` sets `previous = None` when writing back the code the slot already held. `_last_seen` then returns that `None` as-is (via `pending.previous`), and doesn't fall back to `data`.
   - Scenario: the slot holds A. A is rewritten and its result is unknown. Before that write settles, B is written or the slot is cleared.
   - The new record has no `previous`, so a stale read of A counts B as failed right away, or ends the unverified clear.
   - The result is one extra strike or one extra clear.
