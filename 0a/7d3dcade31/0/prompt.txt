1. **`custom_components/lock_code_manager/domain/coordinator.py:459` (medium): clearing a slot can leave it showing a code that is gone.**
   - `drop_pending` removes the `_unconfirmed` record but leaves the stand-in `SlotCredential.unreadable()` in `self.data`. That stand-in was put there by `_give_up`, `_apply_read` or `_give_up_overdue` when the write was kept.
   - `async_internal_clear_usercode` calls `drop_pending` after every clear the driver confirms. So a Z-Wave slot whose kept write is then cleared successfully still shows "present, unreadable". Nothing will correct that value later, because the record is gone.
   - Z-Wave push locks have no periodic read, so the value stays until a driver event or restart. I reproduced this with the first new end-to-end test (`test_a_write_the_lock_never_reads_back_settles_in_sync`). After the successful delete for the disabled user, `coordinator.data` still holds `SlotCredential(present=True, pin=None)` for slot 1, and `_unconfirmed` no longer has slot 1.
   - Sync only reports in sync because of `last_write_was_clear`. Meanwhile the code sensor, websocket and card show a code on the lock for a disabled user.
   - If that user is then deleted, the release finds no owner and the slot is no longer in doubt. The clear returns "nothing changed", `_cleared_slots` loses the slot, and the unmanaged slot keeps showing an unreadable code.
   - Suggested fix: when `drop_pending` removes a record, restore the last value seen from the lock (`_observed`) or empty.

2. **`custom_components/lock_code_manager/providers/_base.py:586` (low): the duplicate-PIN check can miss a kept PIN.**
   - The check looks up `unconfirmed_pins()` only for slots that are in `coordinator.data`. Reads replace `data` wholesale, and the Z-Wave read leaves out unmanaged slots that its cache shows as empty.
   - Scenario: a direct `set_usercode` service call puts PIN X on unmanaged slot 5. The driver can't verify it, so the write is kept. The next refresh drops slot 5 from `data`, though the record stays.
   - Setting X on a managed slot then passes the check that the PR says covers kept PINs. The lock itself then rejects the write as a duplicate.
   - Suggested fix: check `unconfirmed_pins()` on its own as well, not only through `credentials_by_slot()`.
