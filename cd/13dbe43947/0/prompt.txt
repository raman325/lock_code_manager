## 2. The split I'd propose

Each place needs one of two things:
- **The engine needs the position on this lock.** That covers the worker, registry, store, port, releases and repairs. It is what the provider writes, what the store remembers, and what a release clear still targets after the user is deleted.
- **The configuration side needs the user's identity.** That covers the coordinator, the `slot_disabled` and `pin_required` issues, PIN, enabled and condition settings, and attribution names.

**Proposal:**
- **Leave `CredentialAddress` keyed by position.** Only its docstring changes, from "the managed slot number" to "the slot on this lock" (`model/credentials.py:246-248`). Optionally rename `user_ref` to `slot`, which is mechanical.
  - Keying it by user identity instead would force the port to translate back to a position on every read and write (`adapter.py:187,336`). It would also force a store key migration. And pending clears for deleted users would have no identity left to key on.
- **Add two lookups at the boundary between the configuration and the engine (`model/queries.py`):**
  - `user_at(hass, lock, slot) -&gt; (entry, user_id) | None` replaces every `configured_owner(...)` followed by `name_for(slot)` / `slots.get(slot)` / `slot_coordinators.get(slot)`. Call sites: `runtime.py:217-220,236-246,702`, `providers/_base.py:2074-2081`.
  - A per-lock position lookup, e.g. `position(user_id, lock) -&gt; int | None`, used by `SlotEntityCoordinator.async_push_want` for each lock. It is also used by the per-lock entities (`entity.py:407,418`) and when building the `wants` dict at `__init__.py:1792`.
- **Re-key `slot_coordinators` by user identity.** I'd infer subentry id rather than name, given the earlier decision that mutable values stay out of identifiers. That is the identity researcher's call.
- **Fix `forget_entry` and `async_hand_off` to take per-lock positions,** e.g. `Mapping[lock_key, positions]`.

## 3. Allocation

Today every step folds all locks together:
- `async_check_slot_capacity` raises `slot_out_of_range` if any lock can't hold a number (`ha/allocation.py:154-191`).
- `async_max_slot` takes the minimum across locks (`:398`).
- `Occupancy.unavailable` unions every lock's occupied numbers (`model/occupancy.py:67-69`), and `claimed_by_other_entries` is also unioned across locks (`allocation.py:297-303`).

**Per-lock version:** run the same window loop once per lock, each with its own limit (`async_get_max_slot`, falling back to `MAX_SEARCHED_SLOT` at `:395`), its own held positions and its own other-entry claims. It returns `{lock: unavailable}`. `SlotAssignment` becomes name → {lock: slot}, with `held_by` and `reconcile` per lock.

**Simpler:**
- `slot_out_of_range` disappears, along with its config-flow call sites when a lock is added (`config_flow.py:930,1055`).
- The `existing_codes` refusal (`config_flow.py:233-256`) becomes "allocate on the new lock with every user as a newcomer".
- The "smallest lock constrains everyone" minimum goes.
- A code on lock A no longer widens lock B's window. Fewer indices get read (inference).
- `too_many_users` stays, but per lock.

**Harder:**
- **"Reading each lock separately" is not new.** Reads are already per lock and in parallel (`allocation.py:276`).
- Held positions per lock.
- Progress reporting across independent per-lock windows (`:463-472`).
- **"Same number on every lock when one is free everywhere" is a real design decision.** It re-couples the searches: try a common number first, then fall back to per lock. Pure per-lock lowest-free is simpler but makes numbers diverge sooner.
- **Unreadable locks are a design decision.** Today `occupancy_unknown` refuses everything (`:488-493`). Per lock you could allocate on the readable locks and defer the rest.

Matter-style locks (where the slot is not the credential index) only exclude foreign untagged indices (`_async_adoptable`, `:557-578`), which is already per lock. The write-time capacity backstop also stays as it is (`adapter.py:226-235,486-493`).

## 2. What should identify a user

**The earlier reasoning.** `model/slot_assignment.py:10-14` says reusing a number "hands a newcomer the departed user's number, entity identifiers and history, matching what the physical credential slot does." That only holds while the number *is* a physical position on every lock. With per-lock slots, the configuration-wide number no longer names any position. Only the (lock, slot-on-lock) pair still does.

**HA facts (read in source):**
- `ConfigSubentry` is a frozen dataclass whose `subentry_id` is a ULID generated at creation (`config_entries.py:371-379`). It is stored and restored as is (`:482`).
- `async_update_subentry` changes only data, title and unique_id (`:2717-2746`). Nothing can change the id.
- `async_remove_subentry` also deletes the subentry's devices and entities (`config_entries.py:2700-2714`, `helpers/device_registry.py:4444-4453`). So the id lasts exactly as long as the subentry.
- `async_update_entity(new_unique_id=…)` keeps the registry row and the entity_id, records `previous_unique_id`, and raises `ValueError` if the new id is taken (`helpers/entity_registry.py:1959-1970`).
- The recorder only reacts to `old_entity_id` changes (`components/recorder/entity_registry.py:23-43`). History therefore survives a unique_id change.
- `async_update_device(new_identifiers=…)` keeps the device id (so entities stay attached), checks for collisions (`helpers/device_registry.py:3303-3307`), and `merge_identifiers` is deprecated (`:3690`).

| Option | What it is | Registry migration | History and entity IDs | Fit with the reuse reasoning | Main cost |
|---|---|---|---|---|---|
| **(a) Keep the number, add per-lock map** | `CONF_SLOT` stays the user's identity; per-lock slots default to it | None. Every unique_id and device identifier is unchanged | Survive (nothing moves) | Breaks. The number becomes an arbitrary reused handle, and per-lock entities keyed on it track a position that may differ from that lock's real slot | Two meanings share one `int`: every site above must be classified as "user's number" or "slot on this lock". Needs separate types (e.g. a `NewType`) and tests where the two differ |
| **(b) subentry_id** | `{entry}\|{subentry_id}\|{key}[\|lock]`, device `{entry}\|{subentry_id}` | One-way: `new_unique_id` for every entity and `new_identifiers` for every device. Orphans with no subentry must be skipped or purged | Survive (entity_id and device id kept) | Replaces it. Never reused, so a newcomer inherits nothing. That is a behaviour change, but arguably the right one once the number isn't a position | `async_write_entry_config` matches subentries by `CONF_SLOT` (`model/config.py:698-705`), so `EntryConfig` must carry subentry ids. A user created at entry setup gets their id only from HA (`model/config.py:469-477`). The int parsers (`model/config.py:612-662`, `websocket.py:262`) need rewriting |
| **(c1) Hybrid** | Per-user entities and the device keyed by subentry_id; per-lock entities keyed by (lock, slot on that lock) | Per-user entities and devices as in (b). Per-lock entities need none today, since slot = number | Survive | Keeps it exactly where it is true: a per-lock entity tracks a real slot on a real lock | Moving a user's slot on one lock re-keys or recreates that lock's sensors. Tenure makes moves rare |
| **(c2) Number that is never reused** | (a), but new numbers are never handed out again | None on upgrade | Survive | Drops inheritance without moving any key | Numbers drift from slots over time, and the user-facing `code_slot` stops meaning anything |

Two more options I'd rule out. Using the name as identity was tried in PR #1422 and reversed (your memory notes). Using `subentry.unique_id` would get HA to enforce uniqueness (`config_entries.py:2743-2744`), but it is editable and adds nothing over subentry_id.

**A trap common to all four.** A per-lock map keyed by lock entity_id inherits an existing gap: I found nothing that follows a lock rename into `CONF_LOCKS`. My grep for `old_entity_id` hit only the recorder note and `ha/references.py`. The store, by contrast, is keyed by registry id (`__init__.py:1218-1222`). This is an inference.

**How versions work today:**
- `VERSION = 5` with no `MINOR_VERSION` (`config_flow.py:616`).
- `async_migrate_entry` runs a chain 1→2→3→4→5 (`__init__.py:238-500`), each step bumping via `async_update_entry(version=N)`.
- The 3→4 step is pure functions in `model/user_migration.py`, which is registry-silent (docstring lines 19-20), plus an entity_id re-slug.

**What a v5→v6 step would do:** write `{lock: CONF_SLOT for lock in CONF_LOCKS}` into each user subentry, plus the registry re-key under (b) or (c1). Because every per-lock slot equals the old number, the slot each lock is asked to fill is unchanged. So no lock-side change is needed, provided the engine addresses by that per-lock number (the other researcher should confirm).

**Traps for any new subentry key:**
- `from_entry` only strips `CONF_SLOT` (`model/config.py:208-210`), so a new key would leak into user fields.
- `async_update_and_abort` replaces the data wholesale (`config_flow.py:1377-1382`), so reconfigure would erase the map unless it carries it explicitly.
- The edit form only filters `CONF_SLOT` (`config_flow.py:1404`).
- `with_user_renamed` re-keys the assignment (`model/config.py:363-366`), so a per-lock map must be re-keyed with it.
- The "no two users on one number" dedupe (`model/slot_assignment.py:64-77`) becomes a per-lock rule.
