## Read-path findings

I grepped every `CONF_PIN` reference in `custom_components/` and traced each. There are five paths that read a *stored* PIN, and — contrary to the reviewer's framing of "at minimum `pin_value`, and also check `coordinator.py:158`" — **they all funnel through one accessor**, so one site was sufficient. Two sites would have been the wrong answer.

The chain: `SlotEntityCoordinator.pin_value` → `_slot_config()` → `EntryConfig.slot()`, and `LockCoordinator.desired_credential` → `EntryConfig.slot()`. Both land on `EntryConfig._by_slot`, which `__post_init__` builds from `self.users`, which is built exactly once in `EntryConfig.from_mapping`. Normalizing there covers:

| Read path | Reaches | Was leaking |
|---|---|---|
| `slot_coordinator.py:156` `pin_value` | validation | yes |
| `coordinator.py:153` `desired_credential` | **the device write** | yes |
| `util.py:122` deobfuscation table | mask tokens | yes (padded PIN hashed to a different token than the one logged) |
| `text.py` PIN entity | dashboard | yes (rendered `' 4321 '`) |
| `websocket.py` | dashboard | yes |

`from_mapping` is also where `normalize_name` already runs, so PIN stripping is symmetric with the normalization the class already documents itself as doing ("Typed, **normalized** view"). Bonus: `to_dict()` emits the normalized users and feeds `async_update_entry`, so storage heals itself on the next entry write rather than only being papered over on read.

**One place I deliberately did not touch:** `slot_assignment.py:204` (`users_from_slots`) uses PIN truthiness to decide whether a slot represents a person, and it runs *before* my normalization. A slot with a whitespace-only PIN and no name is therefore still kept as a user (now holding an empty PIN, where before it held `"  "`). Changing that would alter v2→v3 migration semantics, which is a one-way door and out of scope. The read is correct either way; only the "is this an empty leftover slot" judgment differs, and it errs toward keeping data.
