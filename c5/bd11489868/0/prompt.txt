## 1. HIGH — `clear_credentials: false` only honours the first name

`/Users/raman/projects/lock_code_manager/custom_components/lock_code_manager/__init__.py:1946-1947`

```python
retained_pairs = runtime_data.retained_pairs
runtime_data.retained_pairs = set()
```

`async_delete_users` stages every departing user's `(lock, slot)` pairs into `runtime_data.retained_pairs` (`domain/services.py:581`) and then makes **one** call to `async_write_entry_config`. But that function is now N writes, not one: `domain/config.py:647` calls `async_remove_subentry` once per departing user, and HA's `_async_update_entry` starts each update listener as an **eager** task. So pass 1 begins executing inside the *first* `async_remove_subentry`, drains the whole `retained_pairs` set, and matches it against a diff that contains only the first user. Pass 2 (started inside the second `async_remove_subentry`) finds `retained_pairs` empty and calls `async_release_managed_slot` on the second user's slot.

Reproduced: entry with `Guest0` (slot 3) and `Guest1` (slot 4), two locks.

```yaml
action: lock_code_manager.delete_user
data:
  config_entry_id: ...
  name: [Guest0, Guest1]
  clear_credentials: false
```

`async_release_managed_slot` was called with `[4, 4]` — Guest1's PIN was wiped from both locks despite the explicit hand-off. Guest0's was correctly retained. The service is documented as "Lock Code Manager stops managing those slots and whatever is programmed there keeps working"; for everyone after the first it does the opposite, irreversibly.

The fix is to discard pairs as they are consumed rather than draining wholesale — e.g. `runtime_data.retained_pairs -= diff.pairs_removed` after the loop, keeping the rest for the passes still to come.

### 1. HIGH — Matter's release path can delete a lock user LCM never created

`/Users/raman/projects/lock_code_manager/custom_components/lock_code_manager/providers/matter.py:847` calls `_find_user_index_for_slot` (defined at `:772`), whose **second** lookup (`:808-817`) adopts *any untagged* lock user that owns a PIN credential at `cred.slot == slot`. `async_delete_user` (`:819`) then issues Matter `ClearUser`, whose spec cascade removes that user and all of its credentials.

That fallback is defensible on the *set* path — it re-adopts a pre-6.0 LCM user and rewrites its name. On the *release* path it is not symmetric: the set path's worst case is a mis-adopted user gets renamed and re-PINned; the release path's worst case is the irreversible deletion of a credential LCM never wrote.

Concrete failure: a Matter lock where the homeowner added a PIN through the manufacturer's app or Apple Home. Matter auto-allocated it credential index 1, and its user is untagged. In LCM you add "Guest", who gets slot 1, and never fill in a PIN (or the lock is offline when the write is attempted) — so no `lcm:1:` user is ever created on that lock. You then delete "Guest". `diff.pairs_removed` is purely configuration-derived (`domain/config.py:457-499`), so the release fires for a slot that never held anything. The canonical pass finds no `lcm:1:` user, the legacy pass matches the homeowner's user at credential index 1, and `ClearUser` destroys it. Nothing in LCM reports why that person is locked out.

Two amplifiers:
- The release loop runs for **every** lock in the entry, not just the one the slot was written to (`__init__.py:1996-2009`). An entry with three Matter locks fires this at all three.
- It is not idempotent in the dangerous direction: the second call for the same slot cannot find LCM's own (now-deleted) user, so it falls to the adoption pass. The docstring at `matter.py:841-845` claims it "tolerates no user found", but the fallback means that branch is often not the one taken.

Recommendation: the release path should use the canonical (tag-matched) lookup only. Give `_find_user_index_for_slot` a flag, or split out a `_find_tagged_user_index_for_slot`, and have `async_release_managed_slot` call that. Adoption belongs to the write path, which can repair a wrong guess; teardown cannot.

### 2. MEDIUM — same adoption flaw in the base default release, via `async_clear_usercode`

`providers/_base.py:1730` (`async_release_managed_slot`) → `async_internal_clear_usercode` → `async_clear_usercode`, whose native-user owner resolution has the identical two-pass structure at `_base.py:1292-1310`. The watchdog is armed strictly later: the call has to traverse the debouncer lock, `_async_refresh`, `async_get_usercodes`, then `_execute_rate_limited`'s two `await`s (`async_is_integration_connected`, `async_is_device_available`, :330-331), `async with self._aio_lock`, and possibly `await asyncio.sleep(delay)` of up to `MIN_OPERATION_DELAY` (2.0s, :91) before reaching `async with self._watching_for_a_stall(...)` at :363. Equal budgets, later start ⇒ the timeout always wins and cancels the watchdog before it fires.

So on the setup path the entire user-visible output for a lock that has not answered in ten minutes is one `LOGGER.info` at :989-994 ("Entities will be created but unavailable until lock is ready"). No warning, no repair, no `lock_stalled`. That is the same class of invisibility as #1523, at the setup end. The PR's own test (`tests/providers/test_base.py::test_setup_does_not_hang_on_a_lock_that_never_answers`) sets `stall_watchdog_seconds` to 0.05 for both and asserts only `last_update_success` and the exception text, so it does not notice.

Recommendation: log at WARNING when the failure was a `TimeoutError` (as opposed to a lock that's merely still booting), or raise the `lock_stalled` issue from the `except TimeoutError:` arm.

## MEDIUM — `lock_stalled` is orphaned when a lock leaves an entry without the entry being deleted

`__init__.py:1320-1323` (the only deletion site) and `_base.py:1158-1168`.

`async_remove_entry` is the sole place that deletes a stall issue, it iterates `config.locks`, and HA calls it only on entry deletion. But a lock can leave an entry with the entry staying alive: `async_release_locks` (`__init__.py:1163`), reached from the options-flow update listener (`__init__.py:2017`) and from `config_flow.py:594`. That path ends at `async_unload_lock(..., remove_permanently=True)` → `lock.async_unload(True)`, which at :1160-1164 explicitly clears the *setup-validation* issue for exactly this reason, then at :1166-1168 cancels the watchdog tasks — and never deletes the stall issue.

Failure scenario: lock L wedges, `lock_stalled_E_L` is raised, the repair text tells the user to fix the lock's integration. The user instead removes L from entry E in the options flow. `async_release_locks` runs, the lock is gone from LCM, and the repair stays up permanently — no code path can produce a matching `_clear_stall_issue()` because the BaseLock is torn down.

Fix is one line beside the existing `_clear_setup_validation_issue()`:
```python
if remove_permanently:
    self._clear_setup_validation_issue()
    self._clear_stall_issue()
```

Two more orphan variants from the same root:
- **Shared instance, first entry removed.** `_lcm_config_entry` is set only in `async_setup_internal` (:899), which the shared-reuse branch at `__init__.py:1756-1765` skips. So the instance keeps entry A's id forever. If A is deleted while B still holds the lock, every subsequent stall report on B's behalf is filed under the *deleted* entry A's id, and `async_remove_entry(B)` deletes `stall_issue_id(B, L)` — a different string. Orphaned.
- **Unbound scope.** `_stall_issue_id` falls back to `f"unbound{id(self)}"` (:458-462). A throwaway allocation provider that stalls and is then discarded before its call returns leaves an id no other object can ever reconstruct. `is_persistent=False` limits this one to the life of the process.

## MEDIUM — the entry-scoping rationale is factually wrong, and its test hand-builds a state the code prevents

`domain/util.py:76-89`, `_base.py:442-463`, `tests/providers/test_base.py::test_one_entrys_recovery_does_not_clear_anothers_stall_report`

Both docstrings assert: "two entries can manage the same lock, each with its own provider instance and its own watchdog." `_find_shared_lock_instance` (`__init__.py:1086-1110`) makes that impossible — there is exactly one BaseLock, one `_aio_lock`, one `_stall_watchdogs`, one `_lcm_config_entry`. Two entries on one lock cannot have two concurrent watchdogs, because they contend on the same `_aio_lock` at :342.

The test reaches its two-instance state by assigning `recovering.lock = stuck.lock` on two independently constructed locks — production has no path that produces that. It is validating the author's assumption rather than the integration, and it is what makes the wrong rationale look verified.

The scoping itself is still worth keeping (it is what makes the `async_remove_entry` cleanup correct), but the stated reason should be replaced with the real one, and the orphan case above is what the docstrings should be warning about.

## MEDIUM — a watchdog that fails is recorded at DEBUG, and the PR's own test certifies the silence

`_base.py:392-411`

Two gaps in the same block:
1. The exception is retrieved **only if the task is already `done()` at that moment**. `async_unload` (:1166-1168) cancels and clears `_stall_watchdogs` without retrieving anything, so a watchdog that already failed and is dropped there produces a stray "Task exception was never retrieved" at GC.

## LOW — the watchdog is a foreground `hass` task, so it blocks `async_block_till_done`

`_base.py:385-388` uses `self.hass.async_create_task(...)`. `HomeAssistant.async_create_task_internal` (core.py:811-812) adds it to `self._tasks`, and `async_block_till_done` (core.py:978-987) waits on `self._tasks` unconditionally.
