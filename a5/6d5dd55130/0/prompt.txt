## Findings (simplification angle, PR #1562)

**1. `custom_components/lock_code_manager/domain/sync.py:374-391` — `_grace`'s two-phase wait is a special case of a one-line loop, and the special case misses the scenario it exists for.**
Failure scenario: stop at t=0, GRACE=30. Some other operation X holds the turn (taken t=20); the tick is queued. Phase 1 ends at t=30, phase 2 is sized from X's `taken` (remaining=20, until t=50). X releases at t=45, the tick takes the turn at t=45, phase 2 expires at t=50 and cancels the tick 5s into its sequence — exactly the mid-sequence cut the second window was added to prevent. Conversely phase 2 extends for a holder that is not a tick at all (the tick is still queued and would be cancelled harmlessly). The two-phase shape encodes "exactly one hand-off" as a structural assumption. Simpler form, same line count, no assumption:
```python
deadline = time.monotonic() + STOP_GRACE_SECONDS
while pending:
    _, pending = await asyncio.wait(pending, timeout=deadline - time.monotonic())
    taken = self._lock.turn_taken_at
    if not pending or taken is None or taken + STOP_GRACE_SECONDS &lt;= deadline:
        break
    deadline = taken + STOP_GRACE_SECONDS
return pending
```
Every wake-up re-derives the deadline from the current holder; the docstring's "one window, then a second" paragraph disappears because there is nothing to narrate.

**2. `custom_components/lock_code_manager/domain/sync.py:348-363` — three-part cancel bookkeeping (`except CancelledError` re-cancel, `if still_running:` log, `for ... cancel`) collapses to one `try/finally`.**
Failure scenario: the next person who touches this block must reason about which of `pending` / `still_running` to cancel in which of three paths (normal, timed out, cancelled). `Task.cancel()` on a done task is a documented no-op (returns False), so cancelling all of `pending` unconditionally is equivalent on every path:
```python
try:
    still_running = await self._grace(pending)
    for task in still_running:
        _LOGGER.info("%s: In-flight tick still running %ss after stop; cancelling it", ...)
finally:
    for task in pending:
        task.cancel()
```
The `except CancelledError: ...; raise` and its "`asyncio.wait` leaves its tasks alone" comment both go; `test_cancelled_stop_cancels_its_ticks` still passes because `finally` runs on cancel. (Folding the log into the loop also fixes the singular "tick" when several are running.)

**3. Grace rationale is written five times — `const.py:222-228`, `sync.py:318-330` (async_stop docstring), `sync.py:377-381` (`_grace` docstring), `providers/_base.py:102-112`, `domain/callbacks.py:187-190`.**

<result>Findings (efficiency angle), in priority order.

**1. `custom_components/lock_code_manager/domain/sync.py:364` — the post-cancel `gather(*pending)` re-opens an operation-budget-sized wait on the unload path for native-user providers**

Failure scenario: the tick is cancelled inside `_execute_locked` (line 434, `_base.py`), which is running `async_set_usercode` → `_set_credential` as the `func` of `_execute_rate_limited` (call site `_base.py:1454`). The `CancelledError` is caught by the new `except BaseException` at `_base.py:1942` and the rollback `await self.async_delete_user(rollback_user_id)` runs *inside* the still-open `asyncio.timeout(budget)` and while `_aio_lock` is still held (the `finally` at 374 hasn't run yet). Matter's `async_delete_user` (`matter.py:854`) is a bare `_invoke_sdk` websocket call with no LCM-side bound; Z-Wave's is `lock_helpers.async_delete_user`. If the device is the one that stopped answering (the premise of the whole PR), the rollback hangs too, and the only thing that ends it is the operation budget: `_operation_budget(3)` = `max(600, per_exchange_budget*3)` seconds, at line 366. `async_stop` then sits in `gather(*pending)` at 364 for the remainder of that budget, so worst-case stop latency is not 2×30s but 30s + (600s − time already spent), i.e. the "unload that waits out the whole budget" the docstring says this PR removes. Cheaper alternative: bound the rollback itself — wrap `await self.async_delete_user(rollback_user_id)` in `asyncio.timeout(STOP_GRACE_SECONDS)` (or a small dedicated constant) when the enclosing exception is a `CancelledError`, then re-raise; that keeps the rollback best-effort on a live lock and bounded on a dead one, and the `finally` releases `_aio_lock` promptly. Alternatively, in `async_stop` replace the unbounded `gather` with `asyncio.wait(pending, timeout=STOP_GRACE_SECONDS)` and log any survivors — but that reintroduces detached work, which #1562 is explicitly trying to eliminate, so bounding at the rollback is the right cut.

**2. `custom_components/lock_code_manager/domain/sync.py:384-390` — `_grace` charges a second full window for a turn that a different caller holds**

Failure scenario: `turn_taken_at` is a per-lock field written by *any* `_execute_rate_limited` call — coordinator reads (`_base.py:2194/2239`), a direct service write, another slot's tick. `_grace` reads it after the first window and, if non-None and recent, waits up to another `STOP_GRACE_SECONDS` regardless of whether the holder is one of `still_running`. Concretely: this manager's tick is queued on `_aio_lock` (never touched the lock, harmless to cancel), a coordinator walk of 30 slots takes the turn 25s into the first window, and stop now waits 30s more for a tick it could have cancelled at t=30s. With many managers stopping concurrently this doesn't multiply, but every one of them pays the same extra window. Cheaper alternative: record the holder alongside the timestamp (`self._turn_holder = asyncio.current_task()` next to `_turn_taken_at = time.monotonic()` at `_base.py:364`, cleared in the `finally`), and in `_grace` only enter the second window when `self._lock.turn_holder in still_running`. Same cost per leaf call (one attribute write), and it removes the extra grace in the common queued-behind-a-read case.

**3. `custom_components/lock_code_manager/domain/sync.py:307` — spawning the first tick via `hass.async_create_task`: confirmed negligible, no cheaper option**

Verification: HA 2025.12's `async_create_task` (core.py:771) defaults `eager_start=True`, so the coroutine runs synchronously inside the call until its first real await; `asyncio.current_task()` inside an eagerly-started task is the new task, so self-registration at `sync.py:760` sees the right task. For the common IN_SYNC/SYNCING/SUSPENDED early return at 766-771 the task completes without ever being scheduled, so the per-entity startup cost is one `Task` object allocation. The alternatives (a `register: bool` flag on `_async_tick`, or skipping registration when `task is` the caller) are not cheaper in any meaningful sense and would leave the initial tick invisible to `async_stop`, which breaks the "nothing of this manager's runs after stop returns" contract. Not a finding to act on.

**4. `custom_components/lock_code_manager/providers/_base.py:364,375` — `_turn_taken_at` on the hot path: negligible, confirmed**

Two attribute stores and one `time.monotonic()` per leaf call, on a path that already calls `time.monotonic()` twice in `_execute_locked` (417, 435) and sleeps for `MIN_OPERATION_DELAY` between operations. No action needed. If finding 2 is adopted, the extra `asyncio.current_task()` per call is likewise noise.

**5. `custom_components/lock_code_manager/domain/callbacks.py:196` — per-slot gather fan-out during unload is bounded, but the concurrency only earns its keep on the subentry path**

Sizing: each slot registers one remover per standard entity (`{slot}|{key}`, entity.py:189) plus one per per-lock entity per lock (`{slot}|{key}|{lock}`, entity.py:355), so roughly 5 + 2×locks removers per slot. `async_unload_entry` (`__init__.py:1245`) already gathers across slots, so with 30 slots × 3 locks the unload now launches ~330 remover coroutines at once, each doing `async_remove(force_remove=True)` + `ent_reg.async_remove`.
