## Issues

### Important

1. **`domain/validation.py:19` — runtime import of `..providers` used only for typing; breaks the domain-module convention and sets up Task 2's import cycle.** `BaseLock` appears only in the signature annotation (deferred by `from __future__ import annotations`); every sibling domain module that needs `BaseLock` only for typing guards it under `TYPE_CHECKING` (`callbacks.py:19`, `exceptions.py:10`, `coordinator.py:39`, `models.py:22`, `sync.py:70` — only `locks.py` imports at runtime, because it calls a function). More than consistency: Task 2 creates the cycle `providers/__init__` → `reader.py` → `domain.validation` → `providers/__init__`, whose survival depends on `BaseLock` being bound before the `reader` import line in `providers/__init__`. Moving this import under `TYPE_CHECKING` now removes the hazard entirely.

2. **The failure event's masked code cannot be deobfuscated, even when it is a configured PIN.** `lock.mask_pin(code)` uses the default `code_slot=0` (`providers/_base.py:411`), but `build_pin_deobfuscation_map` (`domain/util.py:101`) only emits tokens salted with configured slot numbers. For `user_disabled` and `condition_not_met` the submitted code *is* a configured PIN — exactly the cases a user debugging "why didn't my code work" cares about — yet `deobfuscate_log` cannot reverse the token. One-line fix: when `matches` is non-empty, mask with `matches[0].slot_num`; keep slot 0 for unknown codes (irreversible by nature). If irreversibility is the intended privacy posture for this event, record that decision instead.

3. **`services.yaml` selector is lock-only; plan Task 4 specifies `[lock, sensor, text]`.** The Task 1 catalog entry has `domain: lock` for `lock_entity_id`, but readers anchor on sensor/text entities and the plan's Task 4 yaml (and its explicit "`cv.entity_id`, NOT `cv.entity_domain("lock")`" note) requires all three. Accurate today, but since Task 4's implementer may see the `validate_code:` block already present and skip the file, this needs an explicit handoff note or widening now.

### Minor

4. **`domain/validation.py` — the `is_active is None` (never-computed) state silently folds into failure with a misleading reason.** `is_active` is `bool | None`; a coordinator before `async_start`/`_recompute_active` has `(None, [])`, which `_failure_reason` would classify as `condition_not_met`. Unreachable through normal entry setup (`async_start` recomputes at `slot_coordinator.py:110-116`), but a short comment noting the pre-compute state is treated as inactive would prevent a future caller running pre-start from getting a fabricated reason.

5. **Success event's `ATTR_LCM_CONFIG_ENTRY_ID` may not be the validating entry.** `async_fire_code_slot_event` resolves the entry via `find_entry_for_lock_slot` (`providers/_base.py:2086-2091`), independent of the `config_entry` passed to `async_validate_credential`. With one lock in two entries sharing a slot number these can disagree. Using the standard event path is per plan, so this is an observation for the Task 4 multi-entry work, not a defect here.

6. **`ATTR_FIRE_EVENTS`/`ATTR_VALID`/`ATTR_USER` are dead until Task 4.** Plan-directed (Step 1 adds them up front); fine as sequencing, just noting they're currently unreferenced outside `const.py`.

## Issues

### CRITICAL 1 — A reader shared by two LCM entries validates against one entry, and crashes permanently if that entry unloads

`custom_components/lock_code_manager/providers/reader.py:79-85`

`ReaderLock` binds validation to `self._lcm_config_entry`, a single entry. But `BaseLock` instances are **shared across LCM entries** by `_find_shared_lock_instance` (`__init__.py:833-857`, reused at `__init__.py:1425-1435`) — `async_setup_internal` (which sets `_lcm_config_entry`) runs only for the *first* entry; the second entry just does `await existing_lock.async_wait_for_setup()`.

The plan's Task 2 Step 7 explicitly told the implementer to "verify a second LCM entry sharing one reader gets its own instance (each entry's `runtime_data.locks` is per-entry)". It does not. I verified both consequences:

1. **Silent wrong answer.** Two entries, one reader, disjoint slots. A PIN belonging to entry B's slot 5 → `valid=False, reason=unknown_code`, plus a spurious `EVENT_CODE_VALIDATION_FAILED` on every legitimate press. Carol's PIN simply never works, with no error anywhere.
2. **Hard crash.** Unload the *first* entry (the reader survives, owned by entry B). Every subsequent keypad press:

### CRITICAL 2 — The success event carries the submitted credential in cleartext, into the recorder

`providers/_base.py:2116` (`ATTR_STATE`), reached from `domain/validation.py:89`.

`async_fire_code_slot_event` sets `ATTR_STATE` from `hass.states.get(lock.lock.entity_id)`. For a lock that is `locked`/`unlocked`. **For a reader that is the PIN just typed.** Verified:

```

             'action_text': 'Credential validated', 'code_slot': 1, ...}
ATTRS: event.mock_title_alice_credential_used {..., 'state': '1234', ...}

`event.py:126` does `self._trigger_event(lock_entity_id, event.data)`, so the whole payload becomes the event entity's **state attributes** — recorded, visible in more-info, visible in the attributes table, and on the bus for any automation.

The branch went to real trouble to fix two *frontend* cleartext-PIN disclosures (badge, more-info navigation) while the backend path that feeds the recorder leaks the same value. The asymmetry is stark: the *failure* event masks the code (`validation.py:100-104`); the *success* event publishes it. Recommend redacting/omitting `ATTR_STATE` when the anchor is not `lock`-domain (`async_fire_code_slot_event` is `@final`, so this needs to live there or behind a provider property, not an override).

### IMPORTANT 3 — A stale code re-validates when the anchor recovers from unavailable, opening the door unattended

`providers/reader.py:73-79`

The guard only skips `None` / `""` / `unknown` / `unavailable` as the **new** state. It does not look at `old_state`. Verified: `"" → unavailable → "1234"` fires one `credential_used` event, i.e. the user's one-line "on credential_used → open the door" automation runs.

The design's mitigation ("docs recommend the device clear the entity after submission") does not cover it, because the clear happened *before* the outage and the republish restores the pre-clear value only if the device's last publish was the code. ### IMPORTANT 4 — Diagnostics dumps the anchor entity's state verbatim

### IMPORTANT 5 — The two callers of the "one validation core" normalize input differently

## Issues

### Important 1 — fix 4 redacts only the lock being dumped, not its device siblings
`custom_components/lock_code_manager/diagnostics.py:141` passes `_credential_bearing_entity_ids([lock])`, so `_lock_diagnostic` only knows about *its own* anchor. But `_entity_states_for_device` enumerates **every entity on that device**. Two locks sharing a device — two keypad anchors, or (more realistically) a Z-Wave/Zigbee lock whose device also carries a "last used code" sensor that the user configured as a reader anchor — leak the sibling's state. Reproduced verbatim:

```
LOCK A ENTITIES: [{'entity_id': 'sensor.keypad_code', ..., 'state': '**REDACTED**'},
                  {'entity_id': 'sensor.keypad_code_2', ..., 'state': '8888'}]

`async_get_device_diagnostics` hits the same narrow scope at `diagnostics.py:273`. Fix: compute the frozenset once from `all_locks.values()` in both public entry points and thread it into `_lock_diagnostic` — the same shape `_slot_diagnostic` already uses correctly at `diagnostics.py:194`. I confirmed the not-loaded/no-`device_entry` cases are safe: no `runtime_data` means no `locks` key at all, and slot devices only hold LCM's own entities, which the unique-id rule catches.

### Important 2 — fix 3's guard silently disables the reader for an anchor that idles at `unknown`
`providers/reader.py:90` treats `STATE_UNKNOWN` in `old_state` as an outage. But `providers/reader.py:77-82` treats `unknown` in `new_state` as a benign *idle* value (skipped, no failure event). A device that clears to `unknown` rather than `""` between presses is therefore a supported shape on one side and an outage on the other, and **every submission is dropped with no event and no log** — undiagnosable from the user's side.

The current choice is defensible (never open a door unattended beats a working keypad), and the `unknown` clause does cover a real path: a retained-payload device that publishes its last code through `unknown` after a restart. But the trade-off is undocumented and unpinned — there is no test for the `unknown`-idling device in either direction. Minimum ask: a `_LOGGER.debug` on the suppression path so it is diagnosable, plus a wiki note. Worth considering: suppress only when the new value *equals* the last value seen before the blank, which discriminates republish from press without losing either case.

The added tests cover the suppressed cases well but not the legitimate ones. `test_valid_code_fires_usage_event` and my repro #6 cover the `""`-idling path, but no test asserts that a press *after* an outage recovery still fires — worth adding, since it's the property fix 3 must not break.

### Minor 1 — whitespace-only state is not treated as blank (`providers/reader.py:77`)
`"   "` (or a bare `"\n"` from a keypad) passes the blank check, reaches validation, strips to `""`, matches nothing, and fires a `code_validation_failed` event with `code: '&lt;empty&gt;'`. Not a regression (the pre-fix code fired the same event with a different masked value), but stripping in the blank check is the same premise fix 5 rests on. No security consequence: `pin_value` is `... or None`, so `""` can never match a slot.

### Minor 2 — fix 5 strips the submission but nothing strips the stored PIN
`domain/validation.py:86` strips the submitted code; `domain/slot_coordinator.py:259` only collapses *whitespace-only* to `""`, and `config_flow.py:52,79` is bare `cv.string`. ### Minor 3 — `tests/test_diagnostics.py:184` still hardcodes `"**REDACTED**"`
Now that `const.REDACTED` exists, the test should import it; otherwise it asserts against a literal one level away from the code.

### Minor 4 — drive-by, pre-existing

### Note, not a defect
With two entries sharing a reader and the same PIN active in both, only the first entry's `credential_used` event entity fires — so the second user's usage-limiter automation never counts the press. This is the documented "one submission, one verdict" semantic inherited from the service, but readers make multi-entry sharing far likelier. Worth a wiki line.

## Verdict on the unload-leak finding: CONFIRMED, and more severe than described

`_lock_managed_by_other_entry` (`custom_components/lock_code_manager/__init__.py:818-830`) tests config-entry **presence** (`async_entries(..., include_disabled=False)`), not LOADED state, so `async_unload_lock` (`__init__.py:875`) skips `lock.async_unload()` whenever any other non-disabled entry's *config* names the lock — even one that isn't loaded. Three consequences:

1. The anchor listener survives with no entry owning it (the reported leak). This is now **behaviourally inert** thanks to fix 1: `validate_across_entries` returns `None` and the reader ignores it.
2. **It is not inert after a re-setup.** `_find_shared_lock_instance` (`__init__.py:833`) correctly requires `LOADED`, so it finds nothing and builds a *second* `ReaderLock` with a *second* subscription. Both fire. Reproduced: reload entry A while entry B is merely unloaded → **2 `credential_used` events per press**. A door-opening automation runs twice; a usage limiter counts two uses. Reachable by an options change on A while B is in `SETUP_RETRY`, or a reload-all.
3. The same skip leaves the provider's config-entry-state listener registered — which `VirtualLock.async_unload`'s own comment (`providers/virtual.py:65-70`) documents as precisely the dangerous path ("a later provider reload re-runs async_setup against the unloaded Lock Code Manager entry"). That mitigation only runs when `async_unload` is actually called, which is what this predicate skips.

**Where to fix**: not a one-liner across the board — the predicate has four call sites (`__init__.py:818, 875, 1001, 1676`) and the `async_remove_entry` repair-issue cleanup at `:1001` legitimately wants presence, not loadedness. So I would **file it separately** rather than expand this branch. If a scoped fix is wanted here, a `_lock_managed_by_other_loaded_entry` variant used only at `__init__.py:875` is ~5 lines plus a test, and I verified the semantics hold: during HA shutdown the last entry to unload tears the lock down; reloading A while B is genuinely LOADED still shares correctly.
