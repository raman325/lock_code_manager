**What changes the shape of the plan:**

The websocket has to compute per-type status from the lock's sync worker, the same way the in-sync sensors do (`entity.py:417-462`). <result>With only the locks, Matter cannot copy a card from one lock to another: no Matter command ever returns a card's data. The report is at `/tmp/lcm-rfid/matter.md`, with a citation on every claim and the summary table at the end. Sources were the Matter 1.4.2 spec (§5.2), the 1.7 data model, the Matter reference implementation, HA 2026.9 and current HA dev, and LCM `origin/main` (the local `matter.py` is identical).

**1. Writing a card.**
- It is written with `SetCredential` using type RFID and the card's bytes as `CredentialData`.
- The spec says codes are ASCII. Its recommended lengths (8 to 20 bytes) imply the card's UID written as ASCII hex.
- HA's `matter.set_lock_credential` takes `credential_type`, `credential_data`, and optional `credential_index`, `user_index`, `user_status` and `user_type`. For RFID it decodes a hex string to raw bytes, which is not the spec's ASCII convention.
- `matter.clear_lock_credential` and `matter.get_lock_credential_status` also exist.
- What Aqara expects is unknown. Its 10-byte minimum rules out a 4-byte UID in either raw or ASCII-hex form. One retailer says each Aqara card pairs with only one U200 lock; Aqara's own documentation doesn't confirm it.

**2. Reading a card back.** Not possible. The spec forbids returning `CredentialData` for anything except Aliro credentials (phone and wallet keys), and the reference code follows that. You can learn that a card exists at an index, which user owns it, and which fabric (Matter controller) created it. If the creating fabric is empty, the card was added at the lock or in the vendor app. The older command that did return the card's data isn't allowed on locks with user support, like the U300, and is gone from 1.7.

**3. Learning a card.**
- There is no Matter command that puts the lock into enrollment mode.
- The U300 enrolls cards from its own Local Settings menu ("Add Users"), per its manual, and in the Aqara app.
- By spec the lock should then emit `LockUserChange` with data type RFID (7), operation Add, the user index and the card's index. The source field can only be Keypad, Unspecified, Remote or Aliro, never RFID.
- HA doesn't surface this event. LCM subscribes but its handler drops everything except PIN (6) and user (2) changes (`matter.py:2247`).
- Whether the U300 sends this event for cards enrolled at the lock or in the app is unknown.

- **Copy a card to other locks:** not possible. It would need the card's UID read separately, and even then Aqara's encoding is unknown.

**Spec answers:**
