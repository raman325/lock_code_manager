## Finding

**`custom_components/lock_code_manager/providers/zigbee2mqtt.py:892` — medium**

`_process_z2m_device_payload` treats any message on the lock's device topic as proof the lock is reachable. It uses that proof to wake `_async_device_responds`, but Zigbee2MQTT also publishes to that topic from its own cache, without contacting the lock:

- **Home Assistant restart:** When Home Assistant reports itself online, Zigbee2MQTT waits 30 seconds and then republishes every device's cached state. This is in `lib/extension/homeassistant.ts`, in `onMQTTMessage`, which calls `publishEntityState(..., "publishCached")`.
- **Retained messages:** For devices set to `retain: true`, the broker replays the last message when the topic is subscribed to again, for example after a broker reconnect.

Either replay can land inside the 10-second window `_async_device_responds` waits, and it then returns `True` for a lock that is out of range:

1. **A lock with no verdict yet goes wrong.** After five silent reads, the device check passes on the replayed message, so `_async_read_slots` records the lock as not answering. That verdict is saved to the entry data and raises the repair. Allocation (`async_internal_get_occupied_indices`) then treats every unreadable slot as free and can write over a keypad code. The mistake is only undone when the lock later answers a read.
2. **A lock already known to answer goes wrong.** The check at `_mqtt.py:798–801` decides a lock that is silent on every slot is still reachable, so `LockDisconnected` is never raised and the connectivity breaker is never tripped.

**Suggested fix:** only accept a reply to the state request itself. Record the time the request was sent and ignore payloads that arrive before it, or require the payload to carry a fresh `state` or `last_seen` value.
