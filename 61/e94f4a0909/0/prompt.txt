I reviewed PR #1577 (`fix/unconfirmed-writes-retry`, against `origin/main`) and found three real bugs. The ReportFindings tool isn't available in this session (a search for it found nothing), so the findings are only in this reply.

1. **`custom_components/lock_code_manager/domain/sync.py:1125` — high.** The retry wait eventually crashes, because `_unconfirmed_attempts` never stops growing (only the delay is capped).
   - **Cause:** `PENDING_WRITE_TTL * 2 ** (attempts - 1)` turns the integer into a float before `min(..., UNCONFIRMED_RETRY_MAX)` applies the cap. On attempt 1025 that conversion raises `OverflowError`; I confirmed this in Python.
   - **When:** a lock that never confirms (the case this PR targets) retries hourly once the cap is reached, so this hits after about 43 days.
   - **Clear path:** the error is raised inside the `except LockOperationUnconfirmed` handler while the state is still `SYNCING`. `_async_tick` skips `SYNCING` and `request_sync_check` ignores it, so the slot shows "Syncing" forever.
   - **Write path:** the unconfirmed flag has already been consumed and `_unconfirmed_retry_at` is in the past. The next tick writes again right away, and every later write fails the same way, so the retries fall back to roughly once a minute.
   - **Fix:** cap the exponent (or the attempt count).

2. **`custom_components/lock_code_manager/domain/coordinator.py:302` — medium.** The value "restored" when a write is given up can be one that was never confirmed.
   - **Cause:** `before` is taken from `self.data` whenever there is no believed pending write. But `drop_pending` (called from `sync.py:886` when the user changes the PIN during `PENDING_CONFIRMATION`) removes the pending record without taking back the value it pushed into `data`.
   - **Scenario:**
     1. Optimistic write of PIN A.
     2. The user changes the PIN to B, so pending A is dropped and `data` still holds A.
     3. The write of B records `before = known(A)`.
     4. B is given up after a failed read, and `_give_up_overdue` puts `known(A)` back.
   - **Result:** the slot now reports A as the lock's own reading. If the PIN is later set back to A, the slot goes in sync with no write, although nothing ever showed A on the lock.

3. **`custom_components/lock_code_manager/domain/sync.py:541` — low.** On locks that report codes masked, the new "unconfirmed" state doesn't stick and there is no retry. This is the stack the optimistic Z-Wave path mainly exists for.
   - **Scenario:** the slot held a code (unreadable) and the user changes the PIN. The optimistic write sets `_last_set_pin` to the new PIN, and the write is given up after a failed read. The value put back is the unreadable old code.
   - **Result:** the tick shows `UNCONFIRMED` for one tick. On the next tick `calculate_in_sync` returns True (`credential_state == _last_set_pin`), so the slot goes `IN_SYNC` and the wait is forgotten. The slot reads in sync on the strength of the write alone, which the PR says it prevents. The end state matches `main`, so this is a gap in the fix rather than a regression.

Summary:
- `custom_components/lock_code_manager/domain/sync.py:1125` — after about 1025 unconfirmed attempts the retry-delay formula raises `OverflowError`; a clear then sticks in `SYNCING` forever, and writes retry about every minute.
- `custom_components/lock_code_manager/domain/coordinator.py:302` — the `before` value can be a believed value left behind by `drop_pending`, so giving up a later write puts back a PIN that was never confirmed.
- `custom_components/lock_code_manager/domain/sync.py:541` — on masked-code locks, a write given up after a failed read goes back in sync through `_last_set_pin` within one tick, so it is never retried.
