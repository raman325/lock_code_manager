<result>A Matter PIN write now reads only the user recorded for its slot (one `GetUser`) instead of every user on the lock. I opened it as PR https://github.com/raman325/lock_code_manager/pull/1758, commit `3e178ca1` on `fix/matter-write-reads-only-its-user`. All tests pass and `prek` is clean.

**Design** (in `custom_components/lock_code_manager/providers/matter.py`):
- `_find_user_index_for_slot` first calls a new `_recorded_user_for_slot(slot)`. When exactly one user index is recorded for the slot in `_slot_by_user_index`, that user is read with `_raw_lock_user`. It is used only if `_raw_user_slot(user, fabric)` still says it belongs to this slot, so the fabric rule for short tags still applies. Otherwise the existing walk runs, unchanged.
- The read-repair is shared rather than copied. What `async_get_users` did to the two record maps for each user it lists is now a new method, `_record_user(user_index, raw_user, fabric)`, and the single read goes through it too. Both reads update `_slot_by_user_index` and `_pins_by_user_index` the same way; the release path for locks that can't list their users depends on the second. `async_get_users` still keeps entries for users that have vanished.

**Edge-case decisions:**
- **No record:** the map is in memory only and the first poll rebuilds it, so a write before that poll walks, as before.
- **Two or more indices recorded for the slot:** walk, which picks the first listed user, as it always has.
- **Recorded index past `NumberOfTotalUsersSupported`:** walk, and no `GetUser` is sent for that index.
- **Recorded user gone (index reads empty):** the record is dropped, then walk. Without the drop, the old entry plus the newly found one would make the slot ambiguous and force a walk on every later write.
- **Recorded user now tagged for another slot, untagged, or a bare-number name made by another fabric:** `_record_user` corrects the record, then walk.
- **Legacy adoption:** the walk adopts only when no user is tagged for the slot. A user the fast path accepts is tagged for the slot, so it never skips an adoption. When the record is stale the walk adopts as before, including the recorded user itself if it lost its tag.
- **Read fails:** it raises `LockDisconnected` or `LockOperationFailed`, the same types as a failed walk. There is no fallback into a walk and the record is left unchanged.
- **Known limit:** if a second user tagged for the slot appears with no read since, it can't be seen without a walk. The write goes to the recorded user, which still carries the slot's tag, so it is never a wrong user. The next poll records both users and later writes walk.
