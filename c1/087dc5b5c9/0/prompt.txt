<result>## Verdict

The PR fixes the reported symptom (unload/reload no longer blocks) at the right *layer* — the tick is the thing that should be cancellable, and the provider call is the thing that should not be — but the shield is an ad-hoc detachment: it makes the write outlive the tick without making it outlive anything else that dies at unload. Every owner the outliving write reports to (the provider instance, its `_aio_lock`, the coordinator's pending-write table, the tick's error handlers) is torn down by the same unload that cancelled the tick. The design already has the right owner for a detached write (the coordinator, per #1545), but the shield bypasses it on the reload path. Candidates below, strongest first.

---

**1. The outliving write escapes the lock's mutex on reload: two provider instances write the same physical lock concurrently**

file: `custom_components/lock_code_manager/domain/sync.py`, line 521 (`_outlive_tick`); root at `custom_components/lock_code_manager/providers/_base.py` line 237 (`_aio_lock` is a per-instance dataclass field)

Summary: The shielded task keeps holding the *old* `BaseLock` instance's `_aio_lock`. A single-entry reload pops that instance (`async_unload_lock`) and `_setup_one_lock` (`__init__.py` ~1767) builds a fresh one with a fresh `asyncio.Lock`. The new manager's initial tick, and the new coordinator's first refresh, go straight to the device with no serialization against the orphaned write.

Failure scenario: Slow-but-answering lock (the #1397 profile, ~49% response loss, not a total wedge). Reload mid-write. Orphan is sitting inside Matter/Schlage's delete-then-add sequence (`_sequence_lock` is also per-instance). New instance reads the slot, sees the old code (or empty, between the delete and the add), goes OUT_OF_SYNC, issues its own delete+add. Two interleaved delete/add sequences on one credential index — exactly the "door with no working PIN" the shield's docstring says it exists to prevent. The shield trades a *cancellation* hazard for a *concurrency* hazard with the same blast radius.

Deeper change: The mutex must be keyed by the physical lock, not by the provider instance. Move `_aio_lock`/`_sequence_lock` (or the whole in-flight-operation slot) into a domain-level registry in `hass.data[DOMAIN]` keyed by `lock_entity_id`, looked up in `async_create_lock_instance`. This is the same shape as `_find_shared_lock_instance` already uses for multi-entry sharing — extend the "shared instance" idea to the mutex so a rebuilt instance queues behind the orphan (and gets a clean `LockBusy` if it waits too long, which the #1535 machinery already handles correctly). With that in place the shield becomes safe by construction rather than by hope.

---

**2. The write's outcome is discarded entirely; `CodeRejectedError` after a cancel never disables the slot or raises a repair**

file: `custom_components/lock_code_manager/domain/sync.py`, line 521 (`_outlive_tick`), with the handlers at lines ~937-1010 unreachable for a detached write

Summary: After the outer future is cancelled, CPython 3.14's `shield._inner_done_callback` returns early without calling `inner.exception()` (verified from the installed stdlib). The exception is neither routed through the tick's `except CodeRejectedError/LockBusy/LockDisconnected/LockOperationUnsupported/...` ladder nor retrieved — it surfaces only as asyncio's GC-time "Task exception was never retrieved" with no slot context. Breaker accounting, `note_connectivity_failure`, `_disable_slot`, `_suspend_slot`, and the repair issue all silently don't happen. On the success side, `record_write` is a no-op once the coordinator has `_shutdown_requested`, so a polled lock's landed write is also unrecorded.

Failure scenario: User changes a PIN to one the firmware rejects, then reloads (or HA restarts) while the write is in flight. The rejection arrives after the cancel. No repair issue, no slot disable. The new manager's LOADING tick reads the lock, sees the old code, OUT_OF_SYNC, re-writes, rejected again, *now* handled — one full extra rejection cycle and, on a delete-then-add provider, the old code was already deleted by the orphan so the slot is briefly empty. Worse on `LockDisconnected`: the lock breaker is never fed, so the new instance starts at zero strikes against a lock that just proved it isn't answering.

Deeper change: The coordinator already "owns pending writes" (#1545). Make `_outlive_tick` hand the task to it: `coordinator.adopt_write(address, task)` that attaches a done-callback which (a) logs the exception with the slot prefix at the same level the tick would, (b) feeds `note_connectivity_failure` / `_rejected_code_slots` as appropriate, and (c) is itself cancelled-and-awaited in `coordinator.async_shutdown` *with a short bound* rather than left to drift. At minimum, the shield helper needs `task.add_done_callback` that retrieves and logs the exception — the current form is a silent-failure regression relative to main, where the tick's handlers always ran.

---

**3. `SYNCING -&gt; OUT_OF_SYNC` on cancel is a lie about a write that may land, and its only beneficiary is a same-instance restart that production never does**

file: `custom_components/lock_code_manager/domain/sync.py`, line 769

Summary: In production the manager is constructed in `LockCodeManagerCodeSlotInSyncEntity.__init__` and stopped in `async_will_remove_from_hass`; a reload creates a new manager (state `LOADING`). No prod path calls `async_start` on a stopped manager. So the reset's stated purpose ("a restarted manager would never look at the slot again") only holds in tests (`test_async_start_only_tracks_its_own_task` does exactly this). Meanwhile the reset encodes the wrong truth: the write went out; the correct state for "a write went out, confirm by read" is `PENDING_CONFIRMATION`, which the machinery already supports via `coordinator.pending_write`.

Failure scenario: Same-instance restart (the only case where this matters). Write lands after cancel → `record_write` runs in the shielded task (coordinator still alive in this scenario) → next tick after LOADING sees `pending_write` and correctly goes PENDING_CONFIRMATION. So the `OUT_OF_SYNC` reset is redundant with the coordinator path for the landed case, and for the not-yet-landed case the tick would re-issue the write while the orphan still holds `_aio_lock` — which now becomes `LockBusy` after `wait_budget` rather than a clean wait. Not catastrophic, but it is a third place restating the "what is the slot's state after a write" rule (see memory note "release must invert acquire" / drift).

Deeper change: Either drop the reset and let the coordinator's pending table be the single source of truth (the tick already derives PENDING_CONFIRMATION from it), or make the transition a named method on the state machine (`_abandon_in_flight_write()`) that consults `coordinator.has_pending_write(self._address)` and picks PENDING_CONFIRMATION vs OUT_OF_SYNC. Placing it at the tick boundary is fine; placing the *decision* inline in an `except` is what will drift.

---

**4. `_last_set_pin`, the "Set usercode" debug log, and the `return True` now run in the cancellable frame while the write they describe is uncancellable**

file: `custom_components/lock_code_manager/domain/sync.py`, lines 549-561

Summary: `_perform_sync` shields only the provider call. `self._last_set_pin = snapshot.credential_state` and `return True` (which drives `was_set` and the verification branch) sit after the `await` in the cancelled task. The outliving unit is therefore "the device write" but not "the write plus the manager's memory of it."

Failure scenario: Cost is small today only because of finding 3 (no same-instance restart in prod). But on a masked/write-only lock where `_last_set_pin` is the *only* in-sync evidence, a same-instance restart after a cancelled-but-landed write re-sets the PIN unconditionally. And the `was_set=True → record_failure` path is skipped, so an unverified set costs no strike. This is the "one bug hides another" shape: harmless now, wrong the moment anyone adds a restart path.

Deeper change: Move the post-write bookkeeping *into* the shielded coroutine, i.e. shield a small `_write_and_record(snapshot)` that does the provider call, sets `_last_set_pin`, and returns `was_set`. Or, per finding 2, have the coordinator own that memory. Either way the shield boundary should coincide with the unit-of-work boundary, not with the syscall.

---

**5. The unbounded wait isn't gone, it moved to Home Assistant shutdown, where it is now invisible**

file: `custom_components/lock_code_manager/domain/sync.py`, line 528 (`self._hass.async_create_task`, tracked, non-background)

Summary: `hass.async_create_task` puts the write in `hass._tasks`, which `_await_and_log_pending` waits on at each shutdown stage (`STOP_STAGE_SHUTDOWN_TIMEOUT=100`, `FINAL_WRITE_STAGE=60`, `CLOSE_STAGE=30`). A wedged write with a 600 s floor (or ~840 s on ZHA with ten slots per the `_base.py` notes) will blow every stage timeout. Entry unload is fast now; HA restart is not, and the "Timed out waiting for..." log is HA's, not LCM's — nobody will trace it back. Also: within unload, `async_unload_lock` still awaits `lock.async_unload()` → `reconnect_task` cancel-and-await, and `coordinator.async_shutdown()` cancels `_confirm_task` but does not await it; both are fine. The remaining blocker is the shielded write itself at HA-stop time.

Failure scenario: User hits Restart in HA with a wedged Z-Wave lock. Stop stage hangs 100 s, final-write stage 60 s, close 30 s — ~3 minutes of "Home Assistant is shutting down" with HA-level timeout warnings. #1552's complaint was "nothing on screen for all of it"; this is the same experience relocated.

Deeper change: The write should not be tracked as a task HA waits on to completion; it should be a task with an explicit owner that bounds it at shutdown. `hass.async_create_background_task` (excluded from the stage waits) plus an `EVENT_HOMEASSISTANT_STOP` listener owned by the coordinator/registry from finding 1 that cancels it — accepting the mid-sequence risk *only* at process exit, where the alternative is the watchdog killing the process anyway. The `_base.py` comment already argues cancellation is acceptable at the 600 s budget; process exit is the one case where a shorter bound is also acceptable.

**6. `await self._hass.async_create_task(self._async_tick())` in `async_start` papers over `_tick_tasks` self-registration via `asyncio.current_task()`**
