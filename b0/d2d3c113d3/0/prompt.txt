## Findings

**1. `custom_components/lock_code_manager/providers/zwave_js.py:1083` — high: unguarded `self.node` can abort the suspension entirely**

`self.node` raises `LockDisconnected` by design — its own docstring at line 192 says so, and the sibling method directly above (`async_is_device_available`, line 1058) wraps the identical access in `except Exception` for exactly this reason. `describe_link_health` accesses it bare, and `sync.py:791` calls it inside `_async_tick_impl`, which has no exception handling anywhere up the chain (`_async_tick` has only a `finally` that discards the task).

Scenario: the slot breaker trips from repeated `LockOperationFailed`. That path does *not* feed the connectivity breaker, so `self._coordinator.unreachable` is still `False` and the earlier guard at sync.py:768 doesn't fire. If the zwave_js config entry is mid-reload at that moment, `async_get_node_from_entity_id` raises `ValueError` → `LockDisconnected` propagates out of the tick before `_suspend_slot` runs. Result: no repair issue is created, state stays `OUT_OF_SYNC`, `_code_suspend_target` is never recorded, and every subsequent tick re-logs "Sync attempts exceeded" and raises again. The user-visible suspension the PR is trying to enrich is replaced by a traceback loop. Wrap the body (or at least the `self.node` access) and return `None` on failure.

**2. `custom_components/lock_code_manager/providers/zwave_js.py:1084` — medium: the counter that actually signals a mesh problem is the one left out**

Per node-zwave-js `Driver.ts:6640-6650`, `commandsTX` increments *only* on an OK transmit report; a command the node never ACKs increments `commandsDroppedTX` instead. So for the exact failure this feature exists to expose — a lock that has drifted out of range — either:
- nothing ever got through, `commands_tx == 0`, and the method returns `None`, i.e. no information precisely in the worst case; or
- some commands got through earlier, and the repair prints *"0 of 20 commands sent to this lock went unanswered"* followed by *"A large proportion of unanswered commands points to a Z-Wave range or mesh problem rather than the lock refusing the code"* — which affirmatively steers the reader toward "the lock is silently rejecting the code" while the mesh is in fact broken.

`statistics.commands_dropped_tx` should be part of the sentence.

**3. `custom_components/lock_code_manager/providers/zwave_js.py:1090` — medium: "the last round trip" misdescribes `rtt`**

node-zwave-js documents `rtt` as *"Average round-trip-time in ms of commands to this node. Consecutive measurements are combined using an exponential moving average"* (`NodeStatistics.ts:58-62`). Calling it "the last round trip took 1072 ms" tells the reader the most recent exchange was slow; in reality one old outlier keeps the EMA elevated long after the link recovered. This is the same staleness trap the PR carefully guards against for the other counters ("since Z-Wave JS last started") — it just isn't applied to this one. "recent round trips have averaged X ms" would be accurate.

**4. `custom_components/lock_code_manager/providers/zwave_js.py:1087` — low: numerator and denominator count different populations**

`timeoutResponse` increments only for Get-type commands whose response didn't arrive (`Driver.ts:7487`), but the denominator `commands_tx` counts every successfully-sent command, including Sets that never expect a reply. For a lock whose traffic is mostly Sets, the printed proportion systematically understates the response-failure rate, so "a large proportion" never appears even on a genuinely bad link. Either quote the two numbers without framing them as a rate, or ratio over comparable populations.

**5. `custom_components/lock_code_manager/providers/zwave_js.py:1088` — low: the stated window is narrower than the truth**

node-zwave-js describes these as "statistics about the communication with a node since the last reset **or** driver startup". zwave-js-ui exposes a statistics reset, after which "since Z-Wave JS last started" overstates the period the counters cover — the opposite of the misreading the wording was added to prevent.
