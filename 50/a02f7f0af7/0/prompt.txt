**Finding (medium severity):** `custom_components/lock_code_manager/domain/coordinator.py:327`

`drop_pending` now also removes the address from `_unobserved`. The problem is who calls it. `async_internal_clear_usercode` (`providers/_base.py:1572`) calls `drop_pending` after every clear that doesn't raise, including one that found nothing and returned `False`. A clear like that sends nothing to the lock and doesn't change `data`. So the PIN that only the write put there becomes "verified" without any read, push or real clear. The PR says a believed value stays unverified until a read or push mentions it "or a clear replaces it"; this no-op clear replaces nothing.

How it goes wrong on Z-Wave, which uses the native-user clear path:
1. A slot gets an optimistic write of PIN A. The confirmation read fails after the deadline, so `_give_up_overdue` puts the address in `_unobserved`. `data` still shows A, and the driver's cache still shows the slot empty.
2. The user disables the slot, so the target becomes (OFF, A). The tick calls clear. `async_get_users` reads the stale cache, finds no user owning the slot, and returns `False`, so no command goes to the lock. `drop_pending` still runs and removes the address from `_unobserved`. `data` still shows A, now counted as verified, and the slot stays `out_of_sync`.
3. The user re-enables the slot. On the next tick `calculate_in_sync` sees ON with A verified and returns True. The slot goes to `in_sync`, the unconfirmed backoff is reset, and repair issues are cleared, although nothing ever showed that the lock holds A.
4. On a lossy link the drift reads keep timing out, so the slot can show "In sync" indefinitely. That is the #1307 outcome this PR is meant to prevent.

The PR's own tests miss this because they only exercise a clear that actually changes something.

**Possible fix:** only drop `_unobserved` when the clear reported `changed` (or when the clear or its follow-up refresh actually replaces the value in `data`). Keep the pending-drop part as it is.
