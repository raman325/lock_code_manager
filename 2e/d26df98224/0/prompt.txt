- **When it happens:** on Z-Wave, a believed write goes unconfirmed because its confirmation read failed, which leaves the slot marked unverified. The user then disables the slot, and the driver's cache never saw the code.
- **What goes wrong:**
  - Each tick, `async_internal_clear_usercode` finds no owner and returns `False` (the PR's `nothing_to_clear` test case). That means `record_clear` never runs and the slot stays unverified.
  - Z-Wave is a push lock, so sync skips the refresh. `calculate_in_sync` then returns `False` because `is_verified` is false.
  - Because `was_set` is false, nothing is charged to the breaker and the slot goes back to `OUT_OF_SYNC`. The next tick does the same thing.
- **Why it never stops:** this path has no backoff and no breaker. Z-Wave turns off periodic drift reads, and a lock that doesn't hold the code never sends a push for the slot. So nothing ever clears the unverified flag.
- **Result:** the slot re-runs the user and credential cache reads and a rate-limited "clear" every tick indefinitely, and it never shows in sync.
- **What the tests cover:** they only check that the slot isn't in sync after three ticks, so they don't show the loop.

**2. `custom_components/lock_code_manager/domain/sync.py:958` — Low/Medium: the retry wait ignores a lock that now reports a different code.**
- **What the wait checks:** only that the target (enabled state, PIN) is unchanged and the retry time hasn't passed.
- **When it happens:** slot target (on, A) has gone unconfirmed several times, so the wait is now up to an hour. Meanwhile someone sets code B in that slot at the keypad, or another controller does.
- **What goes wrong:**
  - The push updates the coordinator data, but `request_sync_check` does nothing in the `UNCONFIRMED` state.
  - Each tick then finds the slot out of sync, sees the same target, and just stays `UNCONFIRMED`.
  - So a foreign code stays active for up to an hour. On `main`, a slot that loses its code is re-synced right away.
- **Why it matters:** an empty read is ambiguous on this link, but a read showing a *different*, non-empty code is proof the lock doesn't hold A. That case should end the wait.
