## 2. Relevant

**#247 | Lock Code Manager is blocking Home Assistant from finishing startup** — fixed by PR #250, which did two things:
- **(a) Entry setup waits until Home Assistant has started.** Today that's `__init__.py:987-1000`. The spec doesn't touch it. **PRESERVED.**
- **(b) "Don't decide set/clear until we have accurate data from the lock."** PR #250 gated this on `coordinator.last_update_success`. Today the gate is `_resolve_credential_snapshot` returning None when `not self._coordinator.has_credential(...)` (`domain/sync.py:470`), so a slot with no coordinator data is skipped. **NEEDS-SPEC-RULE.**
  - The spec's §5 says that with no informative observation, only belief speaks. It doesn't say whether "the lock has never been read this run" is still gated separately from "a read came back with nothing".
  - Scenario: a fresh install or a lost Store, and the lock's first read raises. Read literally, §5 gives belief ≠ fingerprint(P) for every active slot and belief ≠ "cleared" for every inactive one. Every managed slot is then written or cleared before LCM has heard from the lock. On an unreachable lock those writes raise and charge the slot breaker, which suspends a slot after three. That is the behavior #250 removed.

**#405 | Integration issues ("spamming locks", "clears and sets lock at start")** — no fix PR; it was closed by the 0.6.0 redesign. **PRESERVED, and improved.**
- Today `_last_set_pin` is in memory only (`sync.py:229-234`), and so is `last_write_was_clear`.
- So after every restart, an unreadable or write-only lock is judged out of sync (`calculate_in_sync`, `sync.py:540` and `:557`) and every slot is rewritten.
- The persisted belief in §4 removes that restart rewrite.

**#74 | Switch from binary sensor to sensor** — PR #82 split the sync state into two binary sensors, active and in_sync. A reporter on the issue asked that "PIN synced" go off as soon as the PIN changes and come back on once it is written.
- Under §5 that still holds: a PIN change makes belief ≠ fingerprint(new), so the sensor goes off; when the write returns, belief matches and it goes on. **PRESERVED.**
- **CHANGED-INTENTIONALLY:** the user-visible `sync_status` attribute value `pending_confirmation` goes away. It is defined at `domain/models.py:45`, exposed at `binary_sensor.py:190`, and rendered as "Confirming" at `ts/slot-card.ts:966-973`.
  - On a readable lock, in_sync now turns on as soon as the write returns. Before, it waited for a read to confirm.
  - The spec deletes the state but doesn't mention the card's switch case or the ordering at `sync.py:1150`. Those cleanups need to be in the plan.

**#241 | Not working after install, restart, and setup** — PR #251 made the lock-in-use checks ignore entries that aren't loaded. The code has since split this into two checks:
- `_lock_still_owned_by_another_entry` (`__init__.py:1062`, loaded entries only) is used for live teardown.
- `_lock_managed_by_other_entry` (`__init__.py:1012`, any configured, non-disabled entry, loaded or not) is used for permanent cleanup: `remove_permanently` at `:1104-1110` and `async_remove_entry` at `:1246`.

**NEEDS-SPEC-RULE:** §4 says belief is removed "for a lock when it leaves its last entry" but doesn't name which check decides that.
- Scenario: the loaded-only check gets used. A lock is removed from entry A while entry B, which also manages it, is between loads. B's belief and `answered` flag are deleted. The cost is one rewrite per slot plus a re-armed §9 gap.
- Caveat: `_lock_managed_by_other_entry` passes `include_disabled=False`, so a disabled entry B also loses its belief under the persistent check, not only the loaded-only one.
- The spec should say "same check as `remove_permanently`".

**#61 | Ability to remove a device** — PR #65 added cleanup when a lock is removed from an entry. That is the same lock-removal path in the update listener where §4 adds belief removal. **PRESERVED** (the spec adds to that path, doesn't change it).

## 3. Open feature requests

**#830 (RFID fobs on slots)** — not blocked, but complicated.
- §8 helps: a fob slot that reads as holding a code is "taken", so allocation never overwrites a fob.
- §7 already raises the unmanaged-code repair for it, as today.
- The complication is the §4 belief schema: `{slot}: "pin#…" | "cleared"`, keyed by slot alone and fingerprinted by `mask_pin`.
  - Coordinator data is already keyed by credential address (type + user ref), not slot alone (`coordinator.py:411-431`).
  - Managing RFID, or any second credential type, on the same slot would need a Store version 2 migration.
  - Keying belief by address with a credential-type field now would avoid that migration.

- Belief is keyed by entity registry id, which works for any entity domain, and the §1/§5 model doesn't depend on locks.
- What blocks it today is unchanged: providers and config are built around the lock domain.
- Same caveat as #830: if a panel's codes aren't plain PINs, the PIN-only fingerprint would need extending.</result>

## Findings, most severe first

**F1 — HIGH, NEEDS-SPEC-RULE (#1245/#1246 against §5's Matter re-enable rule).**
- **Where it breaks:** §5 puts the #1538b fix on `set_lock_user`'s update path. That path deliberately swallows every failure (`matter.py:620-639`) on the premise that "only the cosmetic name update is lost". Once it carries `user_status`, a lock that rejects SetUser (the #1245 production `UnknownError … InvalidCommand (0x85)`, or a #1246 charset rejection on all three names) silently keeps the user `occupied_disabled`.
- **Scenario:**
  1. The credential write still returns, and belief is set.
  2. The §3.4 read sees `disabled`, which is charged as a contradiction.
  3. The rewrite repeats. On locks that answer a same-PIN modify with `duplicate`, that is #1044's clear-and-re-add each time.
  4. After 3 tries the slot is suspended with a misleading reason.
- **If the §3.4 read is silent instead:** belief alone reads in sync while the PIN doesn't work. That is the #1538b false in-sync again, and it lasts up to an hour until the drift check.
- **The opposite fix (making UPDATE raise) is also wrong:** it brings back #1245's spurious suspensions.
- **Rule needed:**
  - Pass `user_status` on every name candidate.
  - If every name fails with `MatterError`, issue one status-only modify (`user_name=None` keeps the lock's existing name; see `lock_helpers.py:427-431`) with `user_status="occupied_enabled"`.
  - Only the name may be tolerated. A status write that fails raises `LockOperationFailed`.
  - List this tolerance under §2 as a kept, name-only exception, so nobody deletes it as an "honest writes" violation.
- **Side note:** the modify path indexes `USER_STATUS_REVERSE_MAP[user_status]` directly (`lock_helpers.py:439`). A wrong string raises a `KeyError` that escapes every except clause (`matter.py:620`, `:756-774`) and lands in the sync catchall that suspends the slot (`sync.py:1000-1018`). Pin the exact string with a test through the real helper, which is #1046's lesson.

**F2 — MEDIUM, NEEDS-SPEC-RULE (§3.1's #1523 claim isn't delivered on Matter; touches #1044 and #1049).**
- **Mechanism:** §2/§5 only advance "last write" on a successful completion. A raised write invalidates belief but supersedes no observation.
- **Scenario:**
  1. A new Matter slot has a pre-write observation of `empty`.
  2. `set_lock_credential` times out after the device applied it, which raises `LockDisconnected` (`matter.py:940-948`).
  3. The slot is then disabled.
  4. §5 finds `obs is empty` and returns True, so no clear is issued and the PIN keeps working.
- **Why it lasts on Matter:** nothing re-reads it. There is no poll (`coordinator.py:108`), LCM writes emit no events (`matter.py:992-994`), and the next read is the hourly drift check (#1049). Today has the same hole, so this is not a regression, but the spec says §3.1 fixes it, and the spec's #1523 end-to-end test would fail on Matter.
- **Rule needed:** a raised write records its issue time as a supersession point for every consumer. It sets no belief and no completion time.

**F3 — MEDIUM, NEEDS-SPEC-RULE (#1049 drift check as Matter's only periodic read).**
- **Equality gate:** the drift check publishes only `if new_data != self.data` (`coordinator.py:792`); the same gate is at `:296` and `:507`. If stamps are stored outside the compared values, a fresh read that equals the pre-write values is dropped. Example: after a clear, the lock still reports "holds a code" (Q3). The old stamp then makes the contradiction superseded, and sync reads in sync on belief "cleared". Rule needed: a fresh observation's stamp is news even when its value is unchanged, and no publication gate may drop it.
- **Dropped event — UNVERIFIED:** `matter.py:1545-1548` drops LockUserChange events with lockDataType UserIndex and operation Modify, on the grounds that the event "says nothing about its PIN". I'm assuming an out-of-band status change arrives as exactly that event, per the Matter spec; I didn't verify that in the repo. Under §1's `occupied_disabled` → `disabled`, that justification no longer holds. Until the event triggers a re-read of that user, detection waits for the hourly drift check, which is also skipped while the lock breaker is tripped (`coordinator.py:765-773`).

**F4 — LOW, NEEDS-SPEC-RULE (#1044 path; what does "no change" do?).**
- **Scenario:**
  1. #1044's sync path clears the existing credential (`matter.py:1043-1049`).
  2. The retry raises `DuplicateCodeError`, and the slot is disabled.
  3. The lock now holds nothing, but the pre-write "holds a code" isn't superseded, so §5 issues a clear.
  4. `async_delete_credential` finds no PIN and returns False (`matter.py:1211-1213`).
- **The gap:** §3 says "Returned: set belief and completion time", but it doesn't say whether a "no change" result counts. Today's code deliberately treats a no-op clear as no evidence (`_base.py:1574-1579`). If the spec follows suit, this slot re-issues the clear every tick, uncharged, until the hourly drift check.
- **Rule needed:** state whether "no change" sets belief and the completion time, and whether it triggers the §3.4 read. My recommendation is all three, since the provider's lookup was itself a fresh read.

**Not reported (pre-existing, not caused by the spec):** a PIN swap between two Matter slots makes the lock itself return `duplicate`. §7's LCM-side check doesn't cover that, so one slot is disabled, the same as today.</result>

## Findings, most severe first

**1. HIGH, NEEDS-SPEC-RULE (#737, also hits the #848 case). A same-value re-observation is dropped, so a silently refused write reads as in sync.**
- `push_update` returns early when the new data equals the old (`coordinator.py:567-569`). The Z-Wave report path `_confirm_slot`→`observe_push` (`_base.py:542-552`, `coordinator.py:357`) lands there, and so does the confirmation read when nothing changed (`:507`).
- Today, a refused write still triggers a re-check through three things:
  - the self-push (`known(P)`) changes the data first;
  - otherwise `_failed_writes` plus `async_update_listeners()` fires (`coordinator.py:358-360`, `:509-513`).
- The spec removes all three. Scenario: slot 2 is empty, LCM writes P, and the lock silently refuses it (a duplicate, or a "sent"-only provider). The post-write read says empty, the same value as before, so it is dropped. The stored "empty" keeps its pre-write stamp and is superseded, so belief decides. The slot reads in sync forever and nothing is charged.
- **Rule:** every fresh observation refreshes its stamp and notifies listeners even when the value is unchanged. Only re-published data keeps its old stamp.

**2. HIGH, REGRESSES as worded (#1243). §4 removes a lock's belief record "after `async_unload_lock` on a loaded entry".**
- `async_unload_lock` also runs from `async_unload_entry` (`__init__.py:1207`) on every HA shutdown, reload and disable. #1243 moved persistent cleanup out of unload for exactly this reason.
- Read literally, every restart wipes belief and the `answered` flag. That brings back the restart rewrites (#405). It also clears a flaky lock's flag, so §9 frees its silent slots again (#1581/#1397).
- **Rule:** remove a lock's record only on the permanent-release path (`_async_release_locks`→`async_unload_lock(remove_permanently=True)`, `:1168`). Apply the same downgrade it uses when another entry still manages the lock (`:1107-1111`). Never remove it in `async_unload_entry`. The same applies to deleting `lock_does_not_report_codes`.

**3. HIGH/MED, NEEDS-SPEC-RULE (#737). After the post-write read, the tick must decide the state itself.**
- `request_sync_check` ignores coordinator updates while the slot is SYNCING (`sync.py:699-737`). Today the tick re-checks after its own read (`:1054-1067`), which is what #737's guard relies on.
- §5 says "every returned write is in sync at once", and §3.4 treats the read as "an ordinary observation". If the tick just sets IN_SYNC, a contradiction that arrived during SYNCING is lost until some later data change.
- §6 deletes `take_failed_write`, the one-shot latch that made "charged once" true. The spec doesn't say where the contradiction charge now happens: the breaker may only be changed inside the tick (`:156-162`), and it must be once per write.
- **Rule:** after step 4, the tick evaluates §5 against current observations and charges any contradiction there, at most once per write.

**4. MED, NEEDS-SPEC-RULE (#1050, #987, #1346). The breaker-reset rule leaves sites and mechanisms undefined.**
- "Reset only when an informative observation agrees or the target changes" doesn't address these existing resets:
  - `sync.py:617` (`_disable_slot`, #987);
  - `:629` (`_suspend_slot`);
  - `:724` (resume from suspension when in sync);
  - `:734` (resume after the lock is reachable again, #1346/#532).
- Once `:703` is deleted, the only target-change detector left is `:719-723`, which runs only while SUSPENDED. A target change while OUT_OF_SYNC or IN_SYNC resets nothing. #1050's case (stale counts, then a PIN change to a duplicate) depends on that reset.
- If the rule compares against a stored target, disabling and re-enabling with the same PIN looks like no change. Today `:617` covers that.
- "Agrees" isn't defined for "holds a code". On Matter, where #1050 was found, a successful write would then never clear earlier `LockOperationFailed` charges, while `:1058` does today.
- A consistency note: the agreeing post-write read resets the breaker on every cycle of a slow keypad fight. So the spec's test "keypad fight trips after three (#776)" only holds for fights that overwrite before that read. That isn't a regression, since `:1058` resets today too.

**5. MED, NEEDS-SPEC-RULE (#987, #1243). Repairs get cleared on trust.**
- `_clear_resolved_issues` runs whenever the slot reaches IN_SYNC (`:902`, `:1060`). With in-sync-at-once, a persistent `slot_suspended` or `slot_disabled` repair is deleted the moment a write returns, before the post-write read contradicts it.
- Example: a slot was suspended before a restart (the suspension target lives only in memory). After restart it rewrites, the repair is deleted on return, and then the read contradicts.
- Today, polled providers clear it only after a read-back.
- **Rule:** clear these repairs on the same evidence that resets the breaker (an agreeing observation), or on a returned write only for locks that have never answered.

**6. MED, REGRESSES (#1453 path). The `retained` belief contradicts the `pairs_removed` removal rule.**
- Retained pairs are part of `diff.pairs_removed` (`__init__.py:2108-2122`). §4 removes "a removed user's slots, whatever the release outcome" in that same loop, which deletes the `retained` marker §9 relies on. On a lock that has never answered, allocation then frees the slot and overwrites a code the caller asked LCM to keep.
- §9 also doesn't say which wins between "empty → free" and "retained → taken". If `retained` wins, it never expires, and every add-then-remove cycle burns a slot, which is #1453's second symptom.
- **Rule:**
  - The loop writes `retained` for retained pairs and removes records only for released ones.
  - An informative "empty" observation drops `retained`.

**7. LOW, NEEDS-SPEC-RULE (#1453). Does the release write record belief?**
- The release clear goes through `async_internal_clear_usercode` (`_base.py:1963`), so steps 1-2 of §3 would run. If it records belief after the `pairs_removed` removal, it leaves a per-slot record that the load-time prune never removes, because that prune works per lock.
- **Rule:** either name release writes under §3.6 ("record no belief"), or order the removal after the release.

**8. LOW, NEEDS-SPEC-RULE (#928). Keep the Store object when its file is deleted.**
- "Delete the file when it is empty" must not drop the `Store` object from `hass.data[DOMAIN]`. `async_setup` (`__init__.py:594-597`) won't run again when a new entry is added later.</result>

## Regressions and missing rules, most severe first

**1. NEEDS-SPEC-RULE (HIGH, #817/#1334): the ERROR_UNKNOWN rule in §2 can't be implemented as written.** The spec calls Z-Wave ERROR_UNKNOWN-as-success a violation "even when it carries an explicit rejection". LCM has no way to tell which case it is:
- **Driver:** UC `setCredential` returns the same `Error_Unknown` for "the verification GET didn't confirm" and for "supervised Fail, and the read-back doesn't match" (`AccessControl.ts` ~1183-1226, upstream/master).
- **HA:** `lock_helpers.py:121` turns both into the single key `credential_rejected_unknown`.
- **Consequence:** making it raise would raise on every write to a write-only or masked Z-Wave lock, which is what the provider docstring (`zwave_js.py:631-643`) says this result means. Belief is invalidated each time, three charges suspend a slot whose PIN works, and #1397 comes back.
- **Rule:** ERROR_UNKNOWN stays a returned write with strength `sent`, and §3.4/§5 decide.
- **UNVERIFIED:** whether a verification-GET timeout returns undefined (giving `Error_Unknown`) or throws.

**2. NEEDS-SPEC-RULE (HIGH, #1327/#1471/#819): Disabled is never classified on the Z-Wave push paths or on zwave-js-ui, so "Disabled always contradicts" isn't enforced.**
- **Z-Wave JS shim:** `_uc_slot_in_use` returns `status == ENABLED` (`zwave_js_server/util/lock.py:109-113`), which makes Disabled look the same as Available. A Disabled slot's `userCode` push becomes `known(PIN)`, `known("****")` or `empty` (`zwave_js.py:912-941`).
- **Z-Wave JS read path:** the base projection ignores `User.active`, although the driver maps Disabled to `active=false` (`AccessControl.ts:1620`).
- **zwave-js-ui poll:** a Disabled slot comes back `unreadable` (`zwave_js_ui.py:292-323`), i.e. "holds a code", which is in sync on belief.
- **zwave-js-ui push:** a Disabled status pushes nothing. Its retained `userCode` can arrive before the status (the `True` default) and push `known(PIN)`.
- **Consequence:** a disabled slot holding LCM's PIN reads in sync indefinitely, and §5's clear-then-set trap never fires.
- **Rule:** classify from userIdStatus first (Disabled → `disabled`, carrying the PIN if readable, #1121) on all four paths. Note that zwave-js-ui writes pass `ENABLED` explicitly (`:1299`), so it doesn't need clear-then-set.

**3. REGRESSES (MED-HIGH, #819, already broken on main since #1327): a masked code on an Available slot becomes `known("****")` (`zwave_js.py:932-937`).**
- **Driver behavior:** it persists status before code (`UserCodeCC.ts persistUserCode`), so the code event sees `in_use` False.
- **Scenario:** a slot desired cleared, on a lock that reports Available plus `****`.
- **Consequence under §5:** the masked value is treated as holding a PIN, which contradicts belief "cleared" and is charged. After three, the slot is suspended with a false repair saying the lock still holds a code. #776 is the same alternating-asterisks loop.
- **Rule:** a status of Available means `empty` whatever the code field says.

**4. NEEDS-SPEC-RULE (MED-HIGH, #1344 scenario, #1327 principle): the Z-Wave read reports slots it knows nothing about as `empty`.**
- **Mechanism:** the driver returns no credential when a UC slot's status is missing from its cache (`AccessControl.ts #getCredentialCached_UC`). The base projection then fills it with `empty()` (`_base.py:1621`).
- **Consequence:** on a lock interviewed while asleep, or a write-only lock, every slot reads "empty":
  - §10's "answered" flag gets set.
  - §9 frees slots that may hold keypad codes.
  - The `lock_does_not_report_codes` repair is never raised.
  - Every restart causes a rewrite.
- **Rule:** a missing cache status is `nothing`, not `empty`. #1327 already applies this principle on the push side ("zeros from a partially-loaded cache must not be misread as cleared").

**5. NEEDS-SPEC-RULE (MED, #1334): §2 keeps the reconcile read and says it "becomes" §3.4's post-write read, but doesn't say where it runs.**
- §3.4 runs only after writes that returned, but #1334 also reads before raising a definitive rejection and after a failed delete (Defect 3). Those must stay in the provider.
- On the success path, the read currently runs inside the write call. Anything it produces arrives before the write's completion time and is discarded as superseded (§2/§7). Running §3.4's read as well means two device GETs per write, on the #1397 links where each failed GET holds the lock's turn for the full timeout.
- **Rule:** the success-path read moves to §3.4. Raise-path reads stay in the provider. Both count as "refreshed from the device" for §2's cache rule.

**6. NEEDS-SPEC-RULE (MED, partly UNVERIFIED, #1327/#819): the stale-AVAILABLE guard that §2 keeps only covers the status event (`zwave_js.py:889-909`).**
- The `userCode` event from the same report (`""` or zeros, with `in_use` False) still pushes `empty` (`:914-923`, `:934-935`).
- Today that causes an uncharged rewrite. Under §5 it is a charged contradiction. If #863-class locks send this report after every set, slots get suspended.
- zwave-js-ui's guard does cover the whole report, because a blank code never pushes.
- The spec should define the guard per report, and say whether it applies to §3.4's immediate read. That read is unguarded, and #863's lock sends a stale AVAILABLE about 3 s after a set.
- **UNVERIFIED:** whether those locks' paired `userCode` value changes.

**7. NEEDS-SPEC-RULE (LOW, UNVERIFIED ordering, #1471): §2 only distrusts *retained* zwave-js-ui topics.**
- A *live* value-topic publish can be the driver repeating back LCM's own write (it persists the value after a supervised success). If that publish arrives after the API response, it is taken as the lock agreeing.
- The per-slot "written since last refresh" marks also must not be reset on teardown or resubscribe, which is how `_slot_enabled` behaves today (`:715`, `:1388`).
