## Findings

1. **`custom_components/lock_code_manager/domain/read_health.py:224` (low)** — When a lock is added to an entry, `async_persist_read_health` copies the verdict from the in-memory cache only. It ignores verdicts already stored in other entries, which `read_health()` does count.
   - **Scenario:** after a restart, entry A still has lock X stored as not answering, and the cache is empty. Nothing refills it, because while X is in that state only the hourly probe reads it, and a silent probe records nothing. Entry B then adds X and stores nothing. B's own reads don't write the verdict either: they take the not-answering path, and `async_record_read_health` returns early when the value hasn't changed.
   - **Result:** if X is later removed from A, or A is deleted, the verdict is gone. The repair disappears at the next setup. Allocation on B treats X's unreadable slots as occupied again until X is reclassified, which takes at least five silent reads plus the extra device check.
   - **Fix:** fill from `read_health(hass, lock_entity_id)` rather than `_cache(hass)`.

2. **`custom_components/lock_code_manager/__init__.py:1172` (low)** — `_async_release_locks` deletes the new "lock does not report its codes" repair only after the `runtime_data is None: return` check. When the entry isn't loaded, the repair is never cleared.
   - **Scenario:** entry is loaded, lock X is judged not answering, and the repair is raised. X's entity is then deleted and the entry reloads. Setup fails with "lock can't be found", so Home Assistant has already removed `runtime_data`, and reauth starts. The user swaps X out in reauth.
   - **Result:** `async_forget_read_health` also exits early, because X no longer has an entity registry entry. The repair for X stays up, pointing at a lock the entry no longer manages, until Home Assistant restarts. The repair isn't persistent, so a restart clears it.
   - **Fix:** move the deletion of this repair above the `runtime_data` check, as with the stored-record cleanup.
