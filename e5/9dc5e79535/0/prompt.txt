## NEEDS_CONTEXT — Stage 4 (and therefore Stage 6)

Both existing blueprints scope to **one specific user** via an entity input: `event_entity` (notifier, multiple) and `pin_used_entity` (limiter, single). For the limiter this is load-bearing, not cosmetic — it decrements *that user's* counter and turns off *that user's* switch.

The unified payload carries `name` + `config_entry_id` and **deliberately not the slot**. So the entity input can no longer be matched against the event without a translation step, and there are only two ways out:

**A. Swap the entity inputs for name-based filters** (`users` + `config_entry`), reading `trigger.event.data` directly. Clean, matches the project's name-is-identity direction, and matches the input model you specified for Stage 6. **But it renames/removes a stored input, so every automation already built from these blueprints fails to load.** `slot_usage_limiter.yaml` carries an explicit comment from you saying exactly this is why `pin_used_entity` was never renamed.

**B. Keep the entity inputs and derive the user's name from them** — read the entity's `code_slot`, find the sibling `slot_field == 'name'` text entity in the same entry, compare its state to `trigger.event.data.name`. Preserves stored inputs and capability. The idiom already ships in `calendar_condition.yaml`. **But** it contradicts "reading `trigger.event.data` directly", reintroduces slot-keyed lookups into blueprints just as the project moves off them, and breaks silently if the name entity is unavailable.

I did not guess, because the cost of guessing wrong is either broken user automations (A) or a fragile design the project is actively moving away from (B).

**Related, and I think you should decide both at once:** your Stage 6 blueprint (trigger on the bus event; filter by config entry / users / source / target; user-supplied action sequence) is close to a superset of what a migrated `slot_usage_notifier` would be. ## 2. Could a credential store exist with **no** entity at all?

Mostly yes, but there is **one hard blocker and one seam**, and neither is where the issue implies.

**Hard blocker — availability.** `BaseLockCodeManagerEntity` derives availability *exclusively* from lock-entity states:
- `entity.py:283-287`: `async_track_state_change_filtered(hass, TrackStates(False, {lock.lock.entity_id for lock in self.locks}, set()), ...)`
- `entity.py:229-235` `_is_available`: `any(state.state != STATE_UNAVAILABLE for lock in self.locks if (state := hass.states.get(lock.lock.entity_id)))`

An entry whose *only* member is an entity-less store makes **every LCM entity in the entry permanently unavailable** — PIN text, enabled switch, active sensor, event entity, all of it. `_is_available` returns `False` for an empty/stateless set. This is not a small patch: it's a semantic decision about what "available" means for a store that is always available (`virtual.py:92-94` already answers `async_is_integration_connected → True`).

**Seam — `__post_init__` already tolerates entity-less-ish members.** `_base.py:374-388`: no `device_id` → log a warning, `device_entry` stays `None`, setup continues. Diagnostics (`diagnostics.py:121`) and repair cleanup already branch on `device_entry`. So *device*-lessness is already a supported degradation; only *entity*-lessness isn't.

**What else assumes the entity:**
- `domain/locks.py:37-38`: `lock_entry = ent_reg.async_get(lock_entity_id); assert lock_entry` — a bare assert, the factory's first act.
- `domain/config.py:173` `locks=tuple(mapping.get(CONF_LOCKS, []))` and `models.py:141` `locks: dict[str, BaseLock]` — the config and runtime shapes are both `entity_id -&gt; lock`. An entity-less store needs a synthetic key or a parallel collection. Config-entry `VERSION = 4` (`config_flow.py:262`), so this is a **version 5 migration**.
- `domain/unmanaged.py:65` reads `CONF_LOCKS` straight out of `entry.options/data`, bypassing `EntryConfig`.

**Verdict:** the issue's claim ("if a store doesn't have to *be* a lock, it may not need an entity at all") is **directionally right and structurally cheap** — provider internals, sync, coordinator, allocation and diagnostics all treat `lock.entity_id` as an opaque key. The cost is concentrated in **`entity.py` availability** and a **config-schema version bump**, not in the 256 dereferences. Those are two independent, small-to-medium units and they can land in either order relative to each other, but both must precede any entity-less provider.

### What breaks if `event_types` collapses to a fixed vocabulary

1. **`available` inverts meaning.** `event.py:93-102` returns `False` when no lock supports code slot events. Combined with `_handle_credential_used`'s `if target not in self.event_types: return` (`event.py:184-186`), an entry with **only** non-event-capable locks (Schlage `:79`, Akuvox `:89`, MANUAL-gateway zwave-js-ui `:390`) can record **nothing at all**, even from `use_credential`. **This is the exact mechanism producing the hass-virtual dependency**: `virtual.py:50-61` returns `True` solely so the slot's `event_types` is non-empty and the entity is available. The causal chain the issue asserts is confirmed end to end. A fixed vocabulary makes the entity permanently available and makes `_get_supported_locks` dead for availability purposes — but `_handle_credential_used` still needs *some* recordability predicate, so `_get_supported_locks` doesn't disappear, it just stops being `event_types`.
2. **`websocket.py:856-879` `_get_last_used_info`** reads `event_state.attributes.get("event_type")` and resolves it as a lock entity id to get a friendly name (`:873-876`). Fixing it means reading `target` instead — a coupled Python + payload change that must land in the *same* PR as the event change or the card regresses.
3. **`blueprints/template/lock_code_manager/calendar_condition.yaml:132-133`** — `lock_entity_ids: {{ state_attr(_event_entity, 'event_types') | default([]) }}`. **This is a third shipped blueprint depending on today's `event_types` shape, and #1480 does not mention it.** `lock_entity_ids` is exposed to the user's `condition_template` input. Under a fixed vocabulary it becomes `["credential_used"]` — silently wrong, no error. It's a *variable*, not an input, so it doesn't break blueprint loading, but any user template using it breaks quietly. ## 6. Blueprint migration

**Confirmed: renaming or removing an input breaks existing automations — with an important nuance about *when*.**

Mechanics, from HA source:
- Storage shape: `automations.yaml` holds `{"use_blueprint": {"path": &lt;file&gt;, "input": {&lt;input_name&gt;: &lt;value&gt;}}}` (mirrored at `tests/test_blueprint_behavior.py:94` and `tests/test_repairs_references.py:110-119`).
- `BlueprintInputs.validate` (`components/blueprint/models.py:169-174`): `missing = set(self.blueprint.inputs) - set(self.inputs_with_default)` → raises `MissingInput`. **Only missing keys are checked; extra stored keys are ignored** by `substitute` (`:182`).
  - ⇒ **Renaming an input breaks every stored automation.** Confirms `slot_usage_limiter.yaml:38-40`'s comment.
  - ⇒ **Removing an input is safe for loading** (the stale stored key is ignored). The issue treats rename and remove as equally breaking; removal is not.
  - ⇒ **Adding an input is safe only if it has a `default`.** A new required input is as breaking as a rename.
- **Blueprints are copied into the user's config on import**, so editing the shipped YAML does **not** affect existing users until they re-import. Re-import to the same path requires `allow_override` (`models.py:335-348`, `websocket_api.py:158-197`) and the UI prompts. So an in-place breaking edit hurts *only* users who re-import — but it is silent and irreversible for them.

**What "new version alongside the deprecated original" mechanically requires in this repo:**

   - `tests/test_blueprint_docs.py` (1 parametrized test) — same glob, covered free, subject to (2).

## The shape

`CONF_MEMBERS = "members"` — an optional mapping keyed by entity id, stored **alongside** the `CONF_LOCKS` roster, not inside it. Absent key, and absent member within it, both mean "take the defaults".

- `EntryConfig.members: Mapping[str, Mapping[str, Any]]` — no dataclass default, matching `extra` and for the same reason: an omitted kwarg at a construction site is a `TypeError`, not a silent erasure. All four production construction sites carry it (`config.py` ×3 copy helpers, `services.py` ×2, `config_flow.py` ×1).
- `EntryConfig.member(entity_id) -&gt; Mapping[str, Any]` — returns an empty read-only mapping when nothing is declared, so every field a caller reads takes its own default. Named for a *member of the entry*, not a lock; the docstring says a provider is a credential store and only sometimes the thing that gets locked, and that nothing reading a declaration may assume the member actuates anything. No membership check: declarations are keyed by entity id and outlive removal, so re-adding a member restores what was said about it.
- `_member_declarations()` drops malformed storage at both levels (key not a mapping; a single member's declaration not a mapping) rather than raising — same precedent as `SlotAssignment.from_mapping`. An entry has to load.
- `from_entry` reads it options-then-data per key, like the roster beside it, with a comment on why that's safe here (entity-id-keyed, so a lagging side is inert) where a lagging *assignment* would renumber users.

I chose no `MemberConfig` dataclass: with zero declared fields today it would be an empty box wrapping a mapping, and `users` already uses this exact shape.

## Migration verdict: no bump, no migration

The entry stays at `VERSION = 4`. Every stored v4 entry is *already* a valid instance of the new shape — a key nobody has written reads as "nothing declared", which is precisely what a v4 entry means. A v5 migration would iterate entries and change nothing. Since migrations here are a one-way door, that's pure downside. `#1484` won't need one either as long as its field defaults to off. Downgrades are safe too: an older version reads the key into `extra` and carries it verbatim.

### Issues

**Important — an entity-ID rename silently orphans a declaration, and reauth is where it bites**
`domain/config.py:100-104`, `config_flow.py:565-571`

Entity IDs are mutable in HA. There is no entity-registry-update listener anywhere in this integration, so renaming a lock's entity ID makes its roster entry stop resolving at `__init__.py:780-784`, which fires reauth. The user re-picks the lock, and reauth writes:

```python
data={**get_entry_config(config_entry).to_dict(), **user_input}
```

`user_input` carries the **new** `CONF_LOCKS`; `members` still keys the **old** entity ID. The declaration is orphaned and the new ID silently reads defaults.

The PR defends entity-ID keying by pointing at the roster, but the precedent cuts the other way: **the roster is repaired by reauth; `members` is not.** So this shape is strictly worse than the thing it's modeled on. Under #1484 the concrete outcome is: user renames their codeless lock's entity → reauth → LCM forgets the lock is codeless → starts writing PINs to a lock that can't store them.

Options, cheapest-first: (a) key declarations by the entity registry `entry.id`, HA's immutable handle, which survives renames and is exactly what the "mutable values never go in identifiers" lesson points at; (b) have reauth re-key `members` alongside `locks` when it swaps an ID; (c) accept it and say so in the docstring. What I'd push back on is the current state, where the docstring asserts declarations "outlive the member's removal, so re-adding them restores what was declared" — true for a removal, false for a rename, and the docstring reads as though it covers both.

**Important — nothing tells the user a declaration was discarded (D)**
`domain/config.py:59-76`

The `SlotAssignment.from_mapping` precedent is **real** (`slot_assignment.py:107-110`: non-mapping storage dropped, same "raising would abort setup" reasoning), so the top-level drop is well-founded. But the precedent is single-level; `_member_declarations` extends it to a second, per-member level, which the precedent doesn't cover. And nothing logs.

Today this is inert — no field writes `members`, so the malformed case is unreachable outside hand-edited storage. Under #1484 it stops being inert for the same reason as above. This codebase already has the "we dropped your config, here's what" pattern in two places (`migrate_to_users`'s `dropped` list, the `number_of_uses` repair), so silence here is the outlier. A one-line `_LOGGER.warning` naming the dropped entity IDs would cost nothing and the six parametrized malformed-storage cases are already there to hang it on. This is much cheaper to add now than after a field depends on it.

**Minor — docstring justification doesn't hold**
`domain/config.py:62-63`: "a key written by a version that spelled it differently" is not a case this function can see — a differently-spelled key never reaches `_member_declarations`; it lands in `extra`. The other two examples (hand-edited `.storage`, restored backup) are correct; this third one should go.

**Minor — declarations accumulate with no pruning and no UI**
Nothing ever removes a declaration for a member long gone, and there's no surface to clear one. That is the stated intent, and it is defensible — but it's worth confirming deliberately, because it means "remove the lock and re-add it" will *not* reset a declaration, which is the first thing a user will try when #1484's flag is set wrong.

**Minor — non-string keys survive.** `_member_declarations` filters on the *value* being a `Mapping` but never checks the key, so `{1: {...}}` survives and comes back as `"1"` after JSON round-trip. Unreachable today.

**Minor — `member()` has no production caller.** Only tests reach it; 100% coverage here is test-only coverage. Acceptable for a declared shape-only PR, just don't read the coverage number as evidence the accessor is exercised.

## Keying design chosen

`member()` takes the `er.RegistryEntry` itself, not a registry-id string and not an entity id. Declarations are keyed by `RegistryEntry.id`.

Three reasons, in the order they decided it:

1. **No unresolvable case exists.** `async_setup_entry` (`custom_components/lock_code_manager/__init__.py:786`) refuses to load an entry whose roster holds an entity the registry does not know, and fires reauth. So by the time anything can ask about a member, its registry entry exists — there is no "entity id can't be resolved" policy to invent.
2. **No `hass`/`ent_reg` in a pure dataclass.** Every provider already holds `BaseLock.lock` (`providers/_base.py:205`), so the caller has the object for free.
3. **It closes the silent-wrong-lookup hole.** A registry id and an entity id are both `str`; a `member(registry_id: str)` signature would let a caller pass `"lock.front_door"`, get `{}`, and be told "nothing declared" — the exact failure mode the re-keying exists to prevent. Taking the object makes that a type error instead.

Docstring rewritten to what is now true: a declaration outlives a rename **and** removal from the roster, but not removal from the entity registry (a recreated entity is a new registry entry with a new id and nothing declared).

**No stored data to convert, confirmed.** The only three sites touching `members` (`config_flow.py:667`, `domain/services.py:266,316`) all pass `config.members` straight through; nothing constructs a non-empty value. An absent key still reads as "nothing declared", silently.

## Follow-up issue write-up (reported, not fixed)

**Title: Uses reported while every lock is down are invisible to the blueprints**

Two independent defects on the same seam, both in the availability/recovery path of the per-user `credential_used` entity.

1. *Availability swallows externally-reported uses.* The entity's availability is the shared per-slot rule — at least one of the entry's locks reachable (`entity.py::_is_available`). With every lock `unavailable`, a `lock_code_manager.use_credential` call still records internally (`_handle_credential_used` runs, `_trigger_event` stores the timestamp) but the entity publishes `unavailable`. When a lock recovers, the state surfaces as `unavailable → &lt;timestamp&gt;`, and Slot Usage Notifier deliberately drops exactly that transition (`trigger.from_state.state != 'unavailable'`, added to stop spurious fires on lock recovery). Net: a use reported through the one mechanism designed for uses HA cannot watch is invisible precisely when the locks are down — which is a plausible reason to be using that mechanism. `use_credential` doesn't depend on any lock being reachable, so gating its recording on lock availability is a category error; the fix probably means decoupling this entity's availability from lock reachability, or letting an externally-reported use force the entity available.

2. *Slot Usage Limiter decrements on recovery with no use at all.* Its trigger is a bare `- trigger: state, entity_id: !input pin_used_entity, id: pin_used` — no `not_to`, no `from_state`/`unavailable` guard, unlike the notifier which has all three. An `unavailable → &lt;timestamp&gt;` recovery transition therefore fires it. The new `operation` filter narrows this but does not close it: on recovery the state object still carries the *last recorded* use's attributes, so if that use was an `unlock` the condition passes and the counter drops for an entry nobody made. Also still open: `trigger.to_state is None` (entity removal on unload) is guarded now, but `from_state is None` (first appearance after restart/reload) is not — the notifier guards both. Fix is to mirror the notifier's trigger and condition guards onto the limiter.

Both are pre-existing on `main` in the sense that neither is introduced here, but (1) becomes reachable only now that `use_credential` uses reach the entity at all.

**Refuse**, not inherit silently — but with a change that makes refusing survivable.
