### Important

**1. ZHA: a status-less set the lock dropped still reads in sync when the read-back fails or is answered for another user** (`domain/coordinator.py:243`, `providers/zha.py:436` and `:455`)

- **Cause:** task 2 records a status-less ZHA set as OPTIMISTIC and leaves it pending for the read-back. But `_apply_read` confirms a pending set on any present observation, and unreadable counts as present. ZHA marks a slot unreadable when the read times out on the mesh (`:436`). After task 3, it also does so when the reply names another user (`:455`).
- **Scenario:**
  1. The lock drops `set_pin_code`, which replies with no status.
  2. The read-back of that slot times out, or gets a reply for another user.
  3. The slot is confirmed as `known(pin)` and the in-sync sensor goes on, while the lock holds nothing.
- **Interaction:** this is where tasks 2 and 3 meet. Before task 3, a misattributed reply showing Available would have kept the set waiting. Now it confirms the set.
- **Evidence:** two experiments in scratch, built on the PR's own `unconfirming_lock_table` and `lcm_config_entry` e2e harness, with `applies = False`:
  - `get_pin_code` raising zigpy's `TimeoutError`: table `{}`, `coordinator.data[1] == SlotCredential(present=True, pin='1234')`, nothing pending, in-sync `on`.
  - `misattributed = {1: 2}`: same result, in-sync `on`.
  - Both fail an assertion that the slot is not in sync.
- **Not a regression:** on main, a status-less set was CONFIRMED outright. But it defeats "a set stays pending" on exactly the lossy links where status-less replies are likely, and the e2e tests only cover read-backs that answer cleanly.
- **Fix:** this is the deferred "SlotCredential answers the wrong question" limitation, so I don't think it should block. At least note it in the PR. A real fix would keep ZHA's "read failed" (timeout, misattributed, unparseable) apart from "holds an unreadable code" for pending sets. One option is to leave such slots out of a confirmation-look result, so a set keeps waiting until its deadline.

4. **Edge cases worth a follow-up issue rather than blocking:**
   - **Scope computed early** (`coordinator.py:526`): the look builds its read scope before waiting for the turn. An unconfirmed clear on an unmanaged slot, recorded while the look waits, is left out of that read. The filter then drops it unread, and the replace removes the slot from `data`. It's uncharged and has no breaker, but it isn't "read back" as the docstring says.

The re-sync usually lands, so it's unlikely to reach suspension. Note the asymmetry with sets, which wait until the deadline when the read shows the slot empty.
