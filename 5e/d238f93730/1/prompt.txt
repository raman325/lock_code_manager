## ❌ NEW (MEDIUM) — the api subscription leaks on unload; the deviation in item 2 is the cause

The deviation routes the unsub through the base's `_register_push_unsub`, so its release depends on `teardown_push_subscription()` being called. It never is. `ZWaveJSUILock` does not override `supports_push`, so it inherits `False` (`_base.py:546`), and `_base.py:992` gates the only unload-time teardown on `if self.supports_push:`. Demonstrated empirically:

```
supports_push: False
push unsubs registered after resolution: 1
push unsubs STILL held after async_unload: 1
_api_response_topic after async_unload: zwave/_CLIENTS/+/api/+
```

So every LCM reload leaves an orphaned wildcard subscription behind, holding a reference to the dead provider instance and accumulating per reload. (The `_pending_api_calls` pre-filter keeps each orphan cheap, but they never go away.)

Notably, this violates the documented contract of the very helper it adopted — `_register_push_unsub`'s docstring (`_base.py:333-340`) says its scope is *explicitly* the push-subscription lifecycle and that *"Listeners with a different lifecycle ... do NOT belong here — they must be tracked separately."* The api response subscription lives as long as the **provider**, not as long as a push subscription. `async_unload` is not `@final` and is already overridden by `virtual.py:63` and `zwave_js.py:1054` (the latter for exactly this class of listener) — clean precedent for releasing it there, while keeping `teardown_push_subscription` for the reconnect case.

This is newly introduced: before `062abdea` there was no persistent subscription to leak.
