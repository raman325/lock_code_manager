## NEEDS_CONTEXT — Stage 4 (and therefore Stage 6)

Both existing blueprints scope to **one specific user** via an entity input: `event_entity` (notifier, multiple) and `pin_used_entity` (limiter, single). For the limiter this is load-bearing, not cosmetic — it decrements *that user's* counter and turns off *that user's* switch.

The unified payload carries `name` + `config_entry_id` and **deliberately not the slot**. So the entity input can no longer be matched against the event without a translation step, and there are only two ways out:

**A. Swap the entity inputs for name-based filters** (`users` + `config_entry`), reading `trigger.event.data` directly. Clean, matches the project's name-is-identity direction, and matches the input model you specified for Stage 6. **But it renames/removes a stored input, so every automation already built from these blueprints fails to load.** `slot_usage_limiter.yaml` carries an explicit comment from you saying exactly this is why `pin_used_entity` was never renamed.

**B. Keep the entity inputs and derive the user's name from them** — read the entity's `code_slot`, find the sibling `slot_field == 'name'` text entity in the same entry, compare its state to `trigger.event.data.name`. Preserves stored inputs and capability. The idiom already ships in `calendar_condition.yaml`. **But** it contradicts "reading `trigger.event.data` directly", reintroduces slot-keyed lookups into blueprints just as the project moves off them, and breaks silently if the name entity is unavailable.

I did not guess, because the cost of guessing wrong is either broken user automations (A) or a fragile design the project is actively moving away from (B).

## Verdict on A (the dedupe guard)

**Sound, and it retires cleanly. Merge it — but document the hole.**

- **Can a lock-observed use have `source != target`?** No, structurally: both are the same literal in the one funnel, and a test asserts it. No provider on this branch fires the unified event any other way — the credential reader provider that *would* have (source=reader, target=lock) was deliberately deferred (`c05104cf`). Flag for whoever lands it: that provider is the first thing that can make a lock-observed-style use arrive with distinct ends, and if its lock also fires the deprecated event, the double-record returns.
- **Can a legitimate action call have them equal?** Yes, and this is the hole. Verified by probe: `use_credential(source=lock.X, target=lock.X)` on an in-entry event-capable lock returns `valid: True`, fires the unified event, records nothing on the entity, and logs nothing at any level. Narrow, but it is the *natural* call shape for a lock with an integrated keypad LCM can't watch — exactly the audience the action exists for.
- **Better dedupe in five fields?** No. The true discriminator is "did a lock in this entry observe this," which the payload deliberately cannot express. The alternatives (a one-shot flag set by `_handle_event`, or comparing `__last_event_type`) rely on the synchronous fire-ordering inside `async_fire_code_slot_event` — an implicit invariant that is weaker than the one in use, not stronger. Keep the guard.
- **Retires at #1480 phase 4?** Yes. Deleting the `EVENT_LOCK_STATE_CHANGED` listener, `_event_filter`, `_handle_event`, and the single `and` clause is the whole change, and the hole closes in the same commit. The docstring's claim is accurate.
